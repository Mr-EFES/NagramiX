# NagramiX for Android

The Android application is the second platform in the NagramiX monorepo. Like the iOS application, it is maintained as a small tracked overlay rather than a vendored upstream source tree.

## Base and output

- Upstream: `risin42/NagramX`, pinned to tag `1258` and the exact commit in `android/upstream.env`.
- Version: `0.2.4`.
- Package id: `com.mr_efes.nagramix`.
- CI output: an installable ARM64 debug-signed APK for physical-device pre-release testing.

The debug signature is generated by the isolated GitHub Actions runner and is not a production identity. Updating over a build signed with a different key may require uninstalling the earlier application first.

## Overlay model

`android/apply_overlay.py` verifies the exact pinned Git commit and exact source anchors before applying branding, version/package metadata and NagramiX clean-install defaults. CI checks out NagramX recursively, applies this script and builds the Android application with Gradle. The 30,000-file upstream Android tree is deliberately not copied into this repository.

## Functional parity baseline

NagramX 1258 already supplies the Android implementations for copy/forward modes, saved deleted messages, edit history, story controls, front/rear round-video selection, custom DoH, proxy tools, profile information and the Telegram VoIP Force TCP diagnostic switch. The overlay exposes the matching copy actions and aligns clean-install defaults where the same setting exists:

- Contacts tab hidden;
- tab titles shown;
- story header shown;
- round-video camera starts at the front;
- deleted-message and edit-history storage disabled;
- forward without quote/source and repeat-as-copy actions enabled.

Platform UI and lifecycle details remain native to Android; parity means equivalent user-visible behavior, not shared iOS code.

## Physical-device focus

Test clean install, account login, messaging, copy/forward modes, deleted/edit history, stories, front/rear round video, DoH, proxy recovery, Force TCP calls, notification delivery and background process recovery. Do not treat a successful Gradle build as proof of runtime behavior.
