# Вылет после первого входа: передача открытой базы

Пользователь воспроизводит ошибку в0.5.1–0.5.4: после принятого сервером кода приложение закрывается; после запуска нужен новый вход, со второй попытки работает. Получен журнал0.5.4/build88 с iOS27.0. Установка подписана сторонним способом, но журнал не содержит ошибки подписи или завершения из-за памяти.

## Что установлено

`EXC_BREAKPOINT / SIGTRAP`, упавшая очередь `org.telegram.postbox.Postbox`. Основной поток находится в обычном run loop. UUID `PostboxFramework` из опубликованного IPA совпадает с журналом: `fd4b88d6-d87f-348f-80f8-3a09ddd0f63b`.

Сопоставление Mach-O exports, function starts, инструкций ARM64 и строк SQL:

| Смещение в PostboxFramework | Операция |
| --- | --- |
| `0x1b5c94` | `insertOrReplaceStatement`: аварийная ветка после неуспешного `sqlite3_prepare_v3` для INSERT…ON CONFLICT |
| `0x1bb440`, `0x1bc9ec` | `SqliteValueBox.set` и его thunk |
| `0x1318c0` | `MetadataTable.setUserVersion` |
| `0x174e38` | `openPostbox`: установка первой версии25 при отсутствии метаданных |
| `0x1974a8` | асинхронная closure открытия базы |

Это точная ветка аварии, **не точный SQLite result/error text**: этих данных нет в предоставленном журнале. Нельзя объявлять доказанными повреждение базы, блокировку, ошибочный ключ шифрования, причину в SideStore/iOS27 либо NSUbiquitousKeyValueStore. Полный пользовательский журнал с личными идентификаторами не сохраняется в репозитории.

## Исправление

После публикации авторизованной записи `SharedAccountContext` обычно снова вызывает `accountWithId`, пока тот же `UnauthorizedAccount` держит собственный Postbox. Новый `Account` теперь получает уже открытый Postbox именно этого входа; повторный `openPostbox` на пути продвижения исключён.

Выбор возможен только в основном приложении, когда ID покинул auth record и совпадает с текущим `currentAuth`. Дополнительно TelegramCore проверяет ID, rootPath, basePath и production/test environment. При любом несовпадении остаётся прежнее открытие. Optional-параметр имеет default nil, остальные вызовы прежние.

Штатная транзакция читает реальный `AuthorizedAccountState`; создание Account/Network/keychain, резервные данные и настройка сервисных задач остаются native. Проверено, что штатная транзакция авторизации коммитится перед публикацией результата/запуском AccountManager signal. Передача удерживает Postbox до создания нового Account. Штатный `clearCaches` при удалении `currentAuth` не удаляет базу и не закрывает её, пока новый Account удерживает объект.

Нет нового состояния входа, обхода проверки кода/пароля, удаления базы, пересоздания ключа, автоматического выхода или изменений настроек. Служебный лог содержит только фиксированную строку `Promoting the existing login Postbox`.

Durable-правка: `apply_login_postbox_handoff` в `ios/apply_features.py`, после прежних helper. Два full SHA256 входа и все anchors проверяются **до записи любого файла**. Native Account.swift/SharedAccountContext.swift находятся в proof, а не в составе overlay-репозитория.

## Проверено и осталось проверить

Полный overlay применён к чистому sparse native fixture:453outputs,451побайтно прежних относительно build88, изменены только Account.swift и SharedAccountContext.swift. `scripts/validate_login_handoff.py` проверяет состав, точный обратный diff, изменение каждого из входов и повторное применение без частичной записи. Python compile, существующие3unit tests, release metadata, RU Tour localization, Swift grammar обоих файлов и git diff check прошли.

Это **source_checked / native_compile_pending / device_pending**. Не запускалась новая IPA-сборка; опубликованная0.5.4/build88 остаётся прежней. Правка исключает повторное открытие на данном переходе, но без устройства нельзя утверждать, что все причины повторного входа устранены. Следующий рабочий выпуск0.5.5 только по новой команде пользователя.

Физическая приёмка следующего выпуска:

- Первый успешный вход по коду должен открыть чаты; принудительное закрытие/запуск должно сохранить вход. Проверить SMS/код из другого клиента и email, если доступен.
- Пароль двухэтапной проверки, регистрация, QR/passkey: прежние штатные проверки и переходы.
- Добавление второго аккаунта, переключение между аккаунтами, отмена входа и последующее добавление: без смешивания баз/аккаунтов.
- Уже авторизованный аккаунт при холодном запуске и extension/supplementary paths используют прежнее открытие.
- Штатный выход работает; новый вход после выхода не получает Postbox другого ID/окружения.

Если вылет останется, нужен журнал **нового** пакета с UUID/стеком: он покажет, происходит ли ошибка на прежнем пути или на другом открытии. Для дальнейшего лечения SQLite необходим реальный код/текст ошибки; стирать пользовательскую базу по предположению нельзя.
