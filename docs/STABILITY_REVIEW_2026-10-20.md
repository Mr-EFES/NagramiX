## Что стоит исправить

### 1. Автопереключение может сменить уже работающий прокси — высокий приоритет

Источник: [NagramiXProxyFailoverController.swift](../ios/Sources/TelegramCore/NagramiXProxyFailoverController.swift), `needsConnection`, строки150–158; `reevaluate`, `deadlineExpired` и `selectVerifiedReserve`.

При `.online(proxyAddress: active.host)` контроллер требует ещё и `.available` от отдельного ping. Если ping завершился ошибкой, ещё проверяется или отсутствует в снимке, `needsConnection` возвращает `true`. При включённой автоматике, двух сохранённых серверах и доступном резерве запускается срок переключения, хотя основное соединение сообщает ONLINE. Например, сервер может обслуживать уже открытый сокет и временно не принимать новое проверочное соединение. Периодические проверки способны повторять эту ситуацию.

**Доказательство:** реальное тело `needsConnection` выполнено в standalone Swift с подменой только типов состояния. ONLINE выбранного сервера + успешный ping → false; тот же ONLINE + неудачный/ожидающий ping → true. Отдельный native `recordAvailable` не вызывается из обработки успешного основного соединения. Это воспроизведение решения контроллера, не эксперимент на публичном прокси.

Предложение: основное подтверждённое соединение должно иметь приоритет над независимым ping. Привязать результат к поколению выбора и полному серверу, чтобы старый ONLINE от другого порта того же hostname тоже не подтверждал новый выбор. Проверки резервов оставить; смену запускать по реальной потере/зависанию основного транспорта. Добавить сценарии «ONLINE + ping failed», ручного выбора, одинакового hostname с разными портами и восстановления Wi-Fi/LTE.

### 2. Восстановление связи до авторизации подключено не полностью — высокий приоритет

Источник: [apply_features.py](../ios/apply_features.py), установка DNS observer и failover в `Account`; итоговый `Account.swift`, `UnauthorizedAccount` и авторизованный `Account`.

До входа `UnauthorizedAccount` наблюдает штатные изменения выбранного прокси и VPN bypass. Однако `NagramiXDnsSettingsChanged` observer и `NagramiXProxyFailoverController.start` установлены только в авторизованном `Account`. Следствия:

- при первом входе недоступный выбранный прокси не получает наш автоматический переход на сохранённый рабочий резерв;
- смена DNS/IPv6 до авторизации не инициирует наш предусмотренный reconnect. Новое значение будет прочитано при следующей попытке соединения, но немедленное применение не обеспечено.

**Доказательство:** проверены оба класса и все места создания failover в итоговом overlay. Отсутствие hooks подтверждено по коду; реальный обрыв первого входа на устройстве не воспроизводился.

Предложение: выделить общий сетевой lifecycle для авторизованного и неавторизованного аккаунта, с корректным dispose при смене DC/отмене входа/передаче аккаунта. Не добавлять второй конкурирующий контроллер и не открывать базу заново. Проверить запрос кода, смену прокси во время запроса, email/2FA, второй аккаунт и холодный запуск с сохранённой сессией.

### 3. «Чтение по действию» отправляет слишком широкий запрос для темы — средний приоритет

Источники: [NagramiXReadModeActions.swift](../ios/Sources/TelegramCore/NagramiXReadModeActions.swift), строки42–64; [NagramiXGhostReadActions.swift](../ios/Sources/TelegramCore/NagramiXGhostReadActions.swift). Сравнение: закреплённый Telegram13.0 `TelegramEngine/Messages/ReplyThreadHistory.swift`, `applyMaxReadIndex`.

При наличии `threadId` helper сначала отправляет `channels.readHistory(maxId:)` для всего канала/супергруппы и только затем `messages.readDiscussion` для конкретной темы. Штатный путь чтения темы использует отдельный `readDiscussion`. Дополнительный общий запрос может пометить прочитанными сообщения за пределами выбранной темы; маркер приватного чтения также хранится по peer, без thread.

**Доказательство:** выполнены настоящие helpers с существующими account/network/transaction doubles. Действие в теме2 на сообщении5 породило оба RPC: общий `readHistory(5)`, затем `readDiscussion(2,5)`. Соответствие штатному пути проверено по pinned source. Изменение счётчиков других тем на настоящем сервере ещё не проверено. Имеющийся тест подтверждает оба RPC как ожидаемые, поэтому его успешность не исключает эту ошибку области действия.

Предложение: разделить обычный диалог и тему до отправки RPC; использовать thread-scoped локальное состояние/подтверждение и маркеры. Проверить две одновременно непрочитанные темы, реакцию на третье сообщение, ответ, обычную группу и комментарии канала. Чтение одного контекста не должно разрешать отправку прочтений другого.

### 4. Ошибка сохранения архива скрывается — средний приоритет

Источник: [NagramiXMessageArchive.swift](../ios/Sources/TelegramCore/NagramiXMessageArchive.swift), `persist`, строки230–235 и вызов после обновления памяти в `captureIncoming`.

`JSONEncoder` и атомарная запись используют `try?`; `persist` не возвращает результат. После нехватки места или другой ошибки записи память уже обновлена, а вызывающий код продолжает работу. Пользователь может видеть архив до перезапуска, хотя соответствующие данные на диск не попали. Для индекса медиа используется отдельный throwing-путь, но он не устраняет проблему основного JSON.

**Доказательство:** настоящее тело `persist` выполнено с Foundation и Codable boundary state. Запись в недоступный путь завершается обычным возвратом без файла и без результата ошибки. Это проверка реакции на ошибку файловой системы, не заполнение диска iPhone.

Предложение: возвращать ошибку сохранения, хранить dirty state и ограниченно повторять запись; показывать понятный статус недоступности архива. Обрабатывать ENOSPC отдельно. Не сообщать о долговременном сохранении до успешной записи и не удалять пользовательские данные автоматически.

## Предложения после точечных исправлений

1. **Один общий набор проверок стабильности в CI без IPA.** Сейчас workflow вызывает metadata, применение overlay и intro/debug localization, затем сборку; восемь новых runtime suites не являются обязательным отдельным CI-шагом. Зафиксировать pinned fixture и единый runner, чтобы логика проверялась вместе, включая отрицательные сценарии выше. Для CI потребуется адаптировать historical-delta validators, сохранив их точность.
2. **Ограничить рост архива управляемой политикой.** Сейчас общий JSON перечитывается целиком при запуске и переписывается после изменений, а ограничение суммарного объёма сохранённых файлов отсутствует. На большом архиве это риск памяти, задержек и заполнения диска. Предложение: пакетная/журнальная запись, учёт объёма, предупреждение и пауза новых загрузок при малом свободном месте; очистка старых копий только по явной политике пользователя.
3. **Диагностика соединения без личных данных.** Коды DNS/TCP/RPC, причина выбора/переключения, поколение соединения, длительность восстановления; ограниченный локальный журнал без ключей, номеров, текста сообщений и паролей прокси. Это поможет отличать серверную ошибку, транспорт, VPN и интерфейсное состояние.
4. **Одна общая приёмка после отдельной команды на сборку.** Чистая установка → первый код/2FA → чаты → перезапуск; затем обновление с сохранёнными настройками, второй аккаунт, Wi-Fi↔LTE, отсутствие сети/плохой прокси/рабочий резерв, DNS/IPv6/VPN, foreground/background. Медиа: PiP+звонок/запись/смена качества, Фото с отказанным доступом/малым местом/отменой, приватность в личном чате и двух темах форума. Отдельно проверить системный memory warning и восстановление после принудительного закрытия.

Порядок работ: ложный failover и сетевой lifecycle первого входа → область прочтений темы → ошибки записи архива → единый CI runner → авторизованная тестовая сборка и физическая приёмка. Новые возможности до этой проверки увеличивают число непроверенных сочетаний.
