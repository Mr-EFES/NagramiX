# Редактирование: сохранение результата до снятия ожидания

## Что показала запись

Видео5585920307192649668,26.8с, SHA256 `2e3c335c40e8ad8b8856fc6f125fc732bd43a1a7705a2e1f050b44cdf4075a90`: редактирование обычного текстового сообщения в «Избранном». После первой галочки новый вариант коротко виден, затем возвращается прежний. Следующая попытка и отдельная отправка нового сообщения происходят до завершения синхронизации. Ближе к концу появляется «Обновление…», затем исходное сообщение получает изменённый текст.

Это подтверждает задержку синхронизации, но не позволяет установить состояние радио/интернета, причину задержки и конструктор конкретного RPC-ответа. Видеозапись не содержит сетевого журнала. Найденная ниже ошибка кода воспроизводит возврат старого текста при определённом штатном ответе; считать её доказанной единственной причиной ролика нельзя.

## Подтверждённая ошибка

`requestEditMessageInternal` уже получал медиа из `result.messages` для всех поддержанных контейнеров, но сохранял изменённые сообщения внутри транзакции только в ветке `.updates`. Для `.updatesCombined` и `.updateShort` локальный commit пропускался. После этого во всех случаях вызывался `stateManager.addUpdates(result)` и выдавался `.done(true)`.

Общий `AccountStateManager` передаёт обновления в свою очередь асинхронно. При задержке этой очереди или догрузке состояния native `PendingUpdateMessageManagerImpl` уже снимал optimistic значение, а в Postbox ещё оставался старый текст. В результате только что показанная правка визуально откатывалась до последующей обработки общего потока обновлений.

## Исправление

Стадия53 `edit_result_consistency` следует за `font_preview_apply`. В одном файле `TelegramCore/Sources/PendingMessages/RequestEditMessage.swift` распаковка единственного `.updates` заменена штатными `result.allUpdates`, `result.users`, `result.chats` из существующего `UpdatesApiUtils.swift`. Они уже поддерживают `.updates`, `.updatesCombined` и `.updateShort`.

Все четыре прежних обработчика — `updateEditMessage`, `updateNewMessage`, `updateEditChannelMessage`, `updateNewChannelMessage` — выполняются до `.done(true)` для этих контейнеров. Их тела, incoming flags, local tags, сохранение полного оплаченного контента и сопоставление ресурсов обычных/rich медиа сохранены без изменений, кроме отступов. Событие общего state manager продолжает отправляться ровно один раз.

RPC, параметры/flags, upload/revalidation, права, сроки редактирования, ошибки, `MESSAGE_NOT_MODIFIED`, pending manager и интерфейс не изменены. Нет локальной имитации серверного успеха, дополнительной отправки сообщения, автоматического повтора запроса или новых настроек. Остальные виды ответов сохраняют штатную обработку общего state manager.

## Проверки

[Результаты](EDIT_RESULT_CONSISTENCY_CHECKS.json). Исполняются настоящий полный transaction body сохранения ответа, пять native getter bodies, полный `ChatUpdatingMessageMedia` и `PendingUpdateMessageManagerImpl` с настоящей очередностью снятия pending. RPC/Postbox/Signal queues и хранение API payload представлены явными детерминированными doubles; это не живой Telegram-сервис.

Проверяются три контейнера, четыре сообщения-update, оба incoming направления, full paid media, live-location local tag, users/chats, media/rich resource mappings, медленная общая очередь, отсутствие ответа, прогресс, повторная правка того же ID, поздний ответ отменённого запроса, отказ сервера и `.done(false)`. Старое production тело отдельно компилируется и обязано воспроизвести возврат к старому тексту. Пять смысловых мутаций должны компилироваться, но отвергаться на выполнении, в debug и `-O` с warnings-as-errors.

Все preimages, восемь guards и шаблоны проверяются до первой записи. Ранний обязательный fixture gate получает эту регрессию до overlay; отдельный обязательный validator — после53. Прежние stages/canonical snapshots не меняются. Дополнительно обязательны full inverse/migration/Postbox/member/localization checks.

Полная Apple SDK-сборка, фактические ответы сервера и физическая проверка на iPhone здесь не выполнялись. На следующей разрешённой IPA проверить обычную правку текста и подписи, быстрые повторные правки, слабую сеть и восстановление соединения; именно эти наблюдения подтвердят поведение установленного клиента.
