## Единое состояние и перенос

`NagramiXPrivacySettings` сохраняет прежний единственный `nagramix.privacy.individual.v2`, без нового master. `readMode` имеет только standard/local; старое значение server трактуется как standard. Старый v1 server не должен неожиданно активировать скрытие прочтений под прежним ghost master. Для общего online берётся OR прежних v2 online/automaticOffline; остальные явные значения переносятся точно, включая все OFF. В v1 объединяются только реально активные online/automaticOffline под включённым master. При сохранении нового состояния retired поле automaticOffline не записывается; выключение общего online остаётся OFF после перезапуска и изменения других параметров. В отсутствие старого privacy snapshot default typing ON; латентные опции OFF master не оживают.

`hidesMessageReads` истинно при local **или** readOnAction. `readsOnAction` зависит только от своего checkbox. Поэтому действие может разрешить ровно один scoped read, не открывая глобальный gate. Старые Ghost/ReadMode/Story accessors используют тот же snapshot, старые ключи read-only. Изменение чужой настройки не перезаписывает story choice. Холодный запуск ничего не сбрасывает.

## Реальные исходящие запросы

Прежние worker guards прочтений, consume/mention/reaction receipts, secret-chat suppression, online/offline и история approval/read gate сохранены. ## Скрывать «онлайн»

Fresh default OFF, сохранённый выбор переносится по правилу выше. Один Option.online управляет обеими частями; automaticOffline остаётся только read-only compatibility accessor того же значения. Последнее уточнение пользователя —максимальный офлайн, без искусственного ожидания5секунд. ON сразу подавляет обычные online updates и отправляет account.updateStatus(offline: true). Собственные обновления presence, вход в активный аккаунт/возврат и включение режима подтверждают offline сразу; отдельного стартового таймера нет.

После успешного RPC, способного вернуть online (send/read/typing/reaction/forward/edit/story/call), офлайн запрашивается сразу на очереди этого аккаунта. Network payload/metadata/response/error/cancel/transport/auth и классификатор успешных RPC прежние; свой account.updateStatus исключён, чтобы не создавать цикл. Новая подписка на connectionStatus повторяет offline при переходе соединения в online; повтор одного состояния не создаёт новых запросов. Это сетевое восстановление, а не подмена пользовательского статуса. Пять секунд полностью удалены из presence manager. Native30секундный refresh остаётся fallback и при ON отправляет только offline, в том числе повторяя попытку после RPC error.

Частые события не отменяют уже отправленный offline request. Пока он не завершился, запоминается необходимость ровно одного trailing подтверждения: сервер мог обработать действие после первого offline. После completion оно отправляется через ближайший проход serial queue, без таймера и рекурсии. isPerformingUpdate остаётся true до завершения trailing запроса, сохраняя native network assertion. Новый успешный запрос может покрыть накопившиеся события. Generation и текущий checkbox отклоняют trailing callback после OFF; deinit закрывает подписки/запрос/таймер. Нет бесконечного немедленного retry на ошибке; следующий trigger/reconnect/native refresh повторяет запрос через штатный Network. OFF в foreground возвращает ordinary online, в фоне native offline; read/typing/story настройки независимы.

При недоступной сети отправка ждёт штатное восстановление; iOS suspension не обходится. Telegram и другой клиент могут кратко изменить видимый статус до обработки offline сервером. Нельзя гарантировать постоянный серверный offline по одному локальному checkbox или заявлять физическую работоспособность без теста на iPhone.

## Прочтение по действию

В enqueue граница cloud-истории фиксируется внутри той же транзакции **до** добавления исходящих сообщений. Только успешная немедленная постановка сообщения в очередь разрешает scoped read. Scheduled/nil enqueue и отсутствие границы не разрешают его. Это момент принятия пользовательской отправки, а не гарантия доставки сообщения сервером.

Reaction transaction возвращает только границы действительно добавленных реакций. Отклонённый `shouldApply` (в том числе readonly preview), отсутствующее сообщение и снятие/неизменённый выбор не отправляют read. Группировка альбомов и native pending actions сохранены; отдельный Stars hook сохранён. Для альбома подтверждается native message, которому прикреплена реакция.

`nagramiXReadAfterUserAction` принимает обязательный MessageId. Он не запрашивает новый top позже, не может прочитать другой peer и не переключает глобальную настройку. Self/secret/non-cloud/удалённая граница исключены. Открытие обычного чата после выключения privacy может подтвердить только видимый ранее локальный watermark.

Единый acknowledgement helper отправляет точный maxId и при необходимости thread read. Pts возвращаются state manager. Только успешные ответы (включая boolTrue для channel/discussion) позволяют убрать подтверждённый private watermark. Частичная отметка не удаляет более позднюю границу; ошибка сети/false и приватное чтение во время RPC её сохраняют. Network transport сохраняет штатную обработку соединения; отдельная постоянная очередь повторов read-on-action не добавлена. Повторное действие может повторить неподтверждённую границу.
