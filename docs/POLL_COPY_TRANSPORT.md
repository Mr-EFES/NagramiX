# Самостоятельные опросы с видео: сборка и отправка

После явного выбора пользователя стадия34 [использует native пересылку со скрытым автором](GHOSTGRAM_AUTHORLESS_TRANSPORT.md) для доступного живого опроса: его голосование сохраняет связь с исходным. Правила ниже продолжают действовать при создании именно самостоятельной копии, когда native пересылка недоступна. Строгий API копирования не изменён.

Стадия `poll_copy_transport` после `round_native_playback` подготовлена по видео длительностью41,2с. Копия опроса с видео появляется в личной переписке, получает красную ошибку, повтор также не помогает; штатный репост того же поста проходит. Видео позволяет отделить отказ после enqueue от зависания выбора адресата. Код RPC на записи не виден, поэтому точный серверный ответ конкретного телефона не установлен.

## Изменения

«Переслать» и «Рассылка» продолжают создавать самостоятельные сообщения без forward-заголовка, соответственно одному или нескольким получателям. Новый интерактивный опрос получает собственный LocalPoll ID и голоса. Идентификаторы вариантов создаются так же, как при штатном составлении опроса; правильные ответы викторины переводятся на эти новые идентификаторы. Ограничение голосования подписчиками исходного канала не переносится в самостоятельную копию. Вопрос, порядок и текст вариантов, entities, вложения, объяснение викторины и остальные настройки сохраняются. Ответ неизвестной викторины по-прежнему не придумывается.

Для новой копии sender использует `inputPollAnswer` также у текстовых вариантов. Раньше в этом месте использовалась форма `pollAnswer` с opaque ID полученного опроса. Штатный путь составления/отправки без маркера копии сохраняет прежнее поведение.

Вложенные облачные фото/видео сначала регистрируются для отправки новому адресату через штатный `messages.uploadMedia`, передавая только существующую медиассылку. Это подготовка медиа, отдельного сообщения адресату она не создаёт. Полный видеофайл при действующей ссылке не скачивается и не загружается заново. Одинаковый ресурс нескольких слотов регистрируется один раз, затем подставляется в каждый исходный слот вопроса, варианта и объяснения.

При отказе, относящемся к медиассылке, один раз запрашивается обновлённый оригинал. В копию разрешено переносить только транспортные реквизиты того же медиа, а не новый текст или состояние чужого опроса. Пустое завершение, ошибка или15с ожидания обновления переводят отправку на прежний byte upload. После второго отказа обновлённой ссылки используется byte upload; повторного цикла обновления нет. Локальные файлы и принудительная независимая загрузка сразу идут в прежние загрузчики с сохранённым copy-маркером и исходным partial reference.

Полученный при регистрации результат должен содержать медиа нужного типа и непустой file reference. Неполный ответ не считается готовым вложением. Ошибки прав/авторизации и FLOOD_WAIT не маскируются byte upload; скрытого бесконечного flood-wait при новой регистрации нет. Общий ранее проверенный механизм простоя/отмены/ошибок outbox сохранён.

Исправление не заменяет локальную копию нативной пересылкой или карточкой-ссылкой. Штатный «Репост», отправка без звука и по расписанию, получатели, pending IDs/random_id, ACK/result и повтор существующих сообщений не изменены. Предыдущая правка плеера кружков также закреплена неизменёнными guards.

## Проверено

`python3 scripts/validate_poll_copy_transport.py --source <source29> --swiftc <swiftc> --report <report.json>`.

Исполняются реальные поля/конструкторы модели опроса, копировщик, полная ветка подготовки poll, resolver, обновление медиассылки и настоящий SignalKit. Проверка доходит до итогового `inputMediaPoll`, включая видео, девять текстовых вариантов, multiple/shuffle, отсутствие quiz-полей у обычного голосования и независимые копии трёх адресатов. Проверены фото/видео в вопросе, варианте и объяснении, повтор ресурса, действующая/просроченная/неполная ссылка, пустой/ошибочный/задержавшийся refresh, резервная загрузка, права и отмена. Текстовый `inputPollAnswer` и флаги вложений проверяются в сформированном payload. Типизированные API/Postbox/network/byte I/O являются адаптерами.

## Граница результата

Новая Apple SDK-компиляция, отправка реальному Telegram и физическая приёмка на iPhone не выполнялись. Адаптеры подтверждают код и payload, но не фактическую доставку сервером. Статус новой правки — `compile_pending/device_pending`; опубликованная0.9.2/build193 её не содержит. Новую IPA-сборку запускать только по отдельной команде владельца, следующая версия0.9.3.

На iPhone после новой сборки повторить именно этот пост в «Избранное» и обычную переписку, одному и нескольким получателям, сразу/без звука/по расписанию, при скачанном и нескачанном видео. Проверить целые видео/вопрос/варианты, независимые голоса и отсутствие автора оригинала; затем сетевой обрыв, отмену и повтор без дубликатов. Штатный репост должен сохранить прежнее поведение. Если остаётся отказ, нужен его реальный RPC из диагностического журнала; по одним часам/красной метке его определить нельзя.
