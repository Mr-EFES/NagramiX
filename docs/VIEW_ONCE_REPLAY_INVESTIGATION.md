# Повторное воспроизведение одноразовых сообщений: исследование

Пользователь запросил отдельный выключенный по умолчанию переключатель «Не одноразовые сообщения»: обычное прочтение чата остаётся, подтверждение использования входящего одноразового медиа не отправляется, доступная локальная копия воспроизводится повторно и отправляется пользовательской пересылкой/рассылкой как новое сообщение. Штатный репост оригинала не разрешается. Поведение Telegram на сервере и на втором устройстве требует фактической проверки; никакие гарантии не сделаны.

## Найденные точки

- `TelegramCore/Sources/TelegramEngine/Messages/MarkMessageContentAsConsumedInteractively.swift` одновременно меняет consumable-атрибут, создаёт синхронизируемые операции и начинает Autoremove/Autoclear; выборочная проверка должна выполняться до любой из этих мутаций и только для фактически подходящего входящего одноразового содержимого.
- `GalleryUI/Sources/SecretMediaPreviewController.swift` вызывает этот путь при открытии. `TelegramUI/Components/MediaManager/PeerMessagesMediaPlaylist/Sources/PeerMessagesMediaPlaylist.swift` вызывает его при начале воспроизведения. Чтение истории через `SynchronizePeerReadState.swift` — отдельная операция и не должно подавляться.
- Существуют другие места отправки `messages.readMessageContents`, включая очереди старых операций. Нужен аудит их контекста, а не глобальное блокирование метода: иначе могут пострадать голосовые, упоминания и прочие сообщения. Ранее отправленную операцию отменить на сервере нельзя.
- `NagramiXMessageArchive.captureTemporaryBeforeViewing` зависит от обоих существующих параметров архива; существующие snapshot/renderer показывают удалённое содержимое и используют особое оформление. Новый режим нельзя считать работающим лишь потому, что включён старый архив.
- `ChatController.swift` направляет view-once голосовые/кружки в отдельный просмотрщик. Для нормальной повторной работы нужны поддержка готового полного локального файла, стабильное состояние воспроизведения и идентичность записи; недоступный файл нельзя выдавать за сохранённый.
- `NagramiXContentCopy.swift` допускает особую отправку только собственных одноразовых записей; входящие необходимо обрабатывать отдельным путём копии, без серверного forward. Защищённые/платные/секретные сообщения имеют отдельные ограничения.

## Оставшаяся работа

Добавить сохраняемый переключатель и локализации, закончить проверку путей извлечения фото/видео/voice/round и их полного сохранения, реализовать независимый жизненный цикл локальных файлов и отображение в чате, обеспечить адресную блокировку только подтверждения использования и поддержать отправку готовых локальных копий. Нужны проверки отмены, сбоев, выключения функции, нескольких аккаунтов, сетевых гонок и реального поведения двух аккаунтов на iPhone. На текущий момент функция не реализована; переключатель пользователю не показывается.

## Начальная кодовая подготовка

Стадия `view_once_consumption_guard` добавляет неактивный без отдельного внутреннего ключа `nagramix.messages.replayViewOnce` адресный guard в интерактивную обработку consumption. При внутреннем включении guard применяется к входящим cloud user media с `viewOnceTimeout`, фото/видео/voice/round, исключает платное и уже истёкшее содержимое, до установки атрибута, таймера и операции. Независимый штатный read-history не меняется. UI не включает ключ; функция по-прежнему не реализована. Другие пути consumption/старые очереди, сохранение полного файла, повторное открытие, удаление/рассылка, миграция и конечное поведение сервера ещё требуют работы. Синтаксис и статические guards проверены, SDK/iPhone не проверены.

Следующая внутренняя стадия `view_once_archive_foundation` добавляет отдельный флаг записи архивного ресурса и отдельное разрешение для очереди загрузки, чтобы включение нового режима не включало загрузки остальных временных/удалённых сообщений. Захват перед открытием может сохранять входящее одноразовое медиа независимо от двух прежних настроек архива. Настройка по-прежнему не выведена; показ и пересылка сохранённых записей для нового режима ещё не подключены. Проверены only source guards и синтаксис; фактическую загрузку, миграцию и восстановление файла без Apple SDK/устройства не подтверждали.

Стадия `view_once_archive_render` подключает существующие точки вставки в историю для локально сохранённой одноразовой записи, если исходник истёк или удалён: она выбирает запись при новом флаге независимо от старого архива. При выключенном старом архиве запись для нового режима показывается только при наличии локальных основных ресурсов; временный архивный атрибут не включает метку удаления и полупрозрачность. Это только источник синтетической строки, а не полный end-to-end функционал: пока нет полного маркера одноразовости, переключателя, контекстных действий для живого оригинала, защиты всех путей RPC и проверки фактического воспроизведения. SDK/device pending.

Стадия `view_once_copy_actions` подключает выбор готового локального snapshot для пользовательских действий пересылки без автора и рассылки из меню живого одноразового сообщения. Оригинал не передаётся в эти действия; штатный серверный forward одноразового сообщения отдельно исключён. Snapshot недоступен до сохранения полного основного ресурса. Замена ограничена контекстными действиями и не меняет обычные операции удаления/прочтения живой записи. Проверены статические guards, Swift grammar и обратная source-цепочка, не SDK и не устройство. Остаются настройка, маркер копии, replay всех типов и аудит остальных каналов consumption.

Стадия `view_once_receipt_queue` использует общий внутренний predicate для интерактивного consumption, пакетной очереди consumption, отложенных действий упоминаний/реакций и bulk unread mentions. Только при внутреннем включении и для распознанных входящих одноразовых фото/видео/voice/round в обычном личном cloud-чате точечно исключаются IDs из `readMessageContents`; прочие ID сохраняются. Для bulk lookup выполняется отдельная актуальная транзакция, потому что сетевой ответ приходит после исходной транзакции. Для отсутствующего локально сообщения сохраняется штатный путь: его тип невозможно доказать. Запрос, уже отправленный до включения, отменить нельзя. Очередь не заменяет обычное `readHistory`. Пройдены static guards, grammar и source chain; настоящий MTProto/SDK/device не проверены.

Стадии `view_once_copy_marker`, `view_once_capture_on_receive`, `view_once_setting`, `view_once_preserve_capture`: добавлен маркер сохранённой копии и непрозрачное оформление с подписью «Одноразовое», захват новых подходящих сообщений при приёме, пользовательский переключатель «Не одноразовые сообщения» (fresh OFF и сохранение выбора), сохранение маркировки при повторной синхронизации. Все эти элементы только source-checked. Важно: predicate сейчас рассчитан на `viewOnceTimeout`; обычные фото/видео с конечным коротким таймером не доказаны как покрытые и не следует выдавать их за поддержанные. Не подтверждены полнота всех сетевых путей, реальные download/replay/forward/broadcast и поведение на втором аккаунте; сборка без отдельной команды не запускалась.

Уточнение пользователя: новый режим относится к временному/одноразовому медиа, а отдельный режим удалённых сообщений остаётся самостоятельным. `view_once_short_media` распространяет подготовленные пути на подходящие cloud photo/video/voice/round с нативным short-TTL до 60 секунд, а также viewOnceTimeout. `view_once_server_deletion` при известном server deletion переносит сохранённый replay record в обычный удалённый архив, с видимостью и оформлением по переключателю удалённых сообщений; отдельный локальный обработчик истечения медиа сохраняет replay. Нельзя утверждать, что одинаковые серверные deletion updates всегда позволяют различить удаление отправителем и автоматическое исчезновение: протокольный сценарий требует проверки. SDK, загрузка, playback, receipt и две стороны на устройстве не проверены.

Уточнение: если сообщение удалено отправителем, при OFF «Удалённые сообщения» оно исчезает; при ON показывается локальная копия с меткой удаления, если содержимое удалось сохранить. `view_once_existing_in_chat` инициирует сохранение уже присутствующих в истории подходящих входящих медиа после включения режима; атомарный набор предотвращает повторное резервирование одной записи во время асинхронного захвата. Захват не может восстановить байты после удаления или гарантировать завершение скачивания вовремя. Проверены static guards, source chain и грамматика Swift; SDK, сервер и физический iPhone не проверены.
