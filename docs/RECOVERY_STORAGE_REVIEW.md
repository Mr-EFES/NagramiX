# Проверка жизненного цикла прокси и архива

Последующая команда пользователя: исправить оба дефекта. Изменения после134описаны в [контракте исправления](RECOVERY_STORAGE_FIXES.md); ниже сохранены условия воспроизведения исходного аудита.


Полная цепочка overlay применена к чистому закреплённому Telegram-iOS13.1.1. Снимок содержит298изменённых/добавленных нативных исходников; для анализа сохранены326файлов, включая guards. Подробно проверены последние пути PiP/видео, настройки и запись кружков, сохранение/явный просмотр историй, дерево рассылки, переключение прокси, архив и часть операций чтения/копирования. Это ограниченный анализ клиентского кода, не доказательство корректности всего Telegram и не физический прогон всех функций.

## 1. Автопрокси не восстанавливается при пропущенном foreground после остановки — P2

Файлы: `ios/Sources/TelegramCore/NagramiXProxyFailoverController.swift:57`, `:71`, `:130`, `:172`; путь остановки/старта при shouldKeepConnection — `ios/Sources/TelegramCore/NagramiXNetworkRecovery.swift:72`.

Условие: контроллер получил DidEnterBackground и установил inForeground=false; затем NetworkRecovery остановил его при keep=false. Stop удаляет observers, но не обновляет inForeground. WillEnterForeground приходит, пока observer отсутствует. Повторный start регистрирует observer уже после уведомления и сохраняет false. Проверка enabled отсекает все попытки даже при connecting и исправном резерве. Возврат в приложение сам по себе не исправляет состояние.

Контрольный сценарий исполняет полный реальный класс с детерминированными границами сетевых сигналов/очередей и Foundation NotificationCenter. Обычный запуск при том же отказе переключает на резерв; background→stop→foreground→start не переключает даже после90сек; доставка foreground после start вновь разрешает переключение. В debug и -O результат одинаков. Нативные сокеты не исполнялись; доказана ошибка жизненного цикла контроллера при указанном порядке событий.

Исправление должно синхронизировать текущую активность при каждом start через достоверный foreground-сигнал/снимок и защищать порядок подписки/начального значения; простая безусловная установка true будет неверна для запуска в фоне.

## 2. Очистка архива удаляет файл нового резервирования — P2

Файлы: `ios/Sources/TelegramCore/NagramiXArchivedMediaStore.swift:140`, `:146`, `:196`; `ios/Sources/TelegramCore/NagramiXMessageArchive.swift:693` (clearAll) и :303(didPersist).

Условие: перед выполнением очистки новое сообщение резервирует уже сохранённый в архиве ресурс с ticket больше clearTicket. Clear сохраняет это новое резервирование, но безусловно обнуляет files и удаляет весь каталог. В результате защитная запись остаётся, а её локальные байты исчезают. Дополнительно clearAll вызывает barrier() без clearFiles=true, поэтому до очистки resourcesToRemove продолжает разрешать удаление такой копии из MediaBox, полагаясь на существующий архивный файл.

Проверка исполняет фактические методы reserve/barrier/resourcesToRemove/clear/filePath/existingPath без изменения их тел; ресурсные DTO и побочные callbacks представлены границами. Реальный FileManager создаёт файл, резервируется новый ticket, затем clear(before:olderTicket) оставляет резервирование и физически удаляет файл. Debug и -O воспроизводят одинаковый результат. Полный сетевой/MediaBox сценарий не исполнялся. Для повторно используемого вложения при таком наложении операций локальная архивная копия теряется; если исходные байты ещё доступны, возможна повторная загрузка, но сохранность новой копии не обеспечена.

Исправление должно согласовать файловую очистку с новыми резервированиями и удержанием MediaBox до повторного сохранения; одной фильтрации reservations по ticket недостаточно. Сохранять требование: очищать старые байты только после успешного коммита JSON.

## PiP и ограничения проверки

Пользователь подтвердил отказ PiP на iPhone в134. Точная причина этого отказа пока не установлена: нет кода/этапа отказа и уточнённого поведения кнопки/свайпа. Не объявлять какой-либо аудио/visibility/killswitch сценарий установленной причиной по одному чтению исходников.

Существующие проверки PiP проходят:587gesture,588lifecycle и actual start-wrapper/visual в debug/-O. Но transaction harness задаёт readiness готовым значением; он не исполняет системное isPictureInPicturePossible и не доказывает запуск AVKit. Поэтому их успех не снимает физическую проблему. Проверки кружков также прошли:21font expressions,12capture/export presets,24page transitions,36format predicates с указанными тестовыми границами. Новый Apple SDK/IPA и реальный UIKit/AVFoundation/камера/Photos/сервер не запускались.
