# Расшифровка одноразовых голосовых

Актуальный маршрут для сохранённых временных сообщений заменён стадией33: [транскрибация без открытия](PRIVATE_TEMPORARY_TRANSCRIPTION.md). Старое допущение ниже о безопасности native Telegram RPC по ID одноразового оригинала больше не применяется: используется безопасное распознавание аудио, а Core блокирует этот RPC. Кружки и секретные чаты поддерживаются последующими стадиями. Остальной текст описывает историческую реализацию и её проверки.

Поздняя стадия `temporary_voice_transcription` после `app_language_localization`. Изменения подготовлены в исходниках; Apple SDK и физическая проверка ожидаются. Опубликованный 0.8.5/build165 их не содержит. Сборка и публикация не запускались.

## Поведение

При активных «Временных сообщениях» поддерживаемая одноразовая голосовая получает обычную кнопку `→A`. Текст раскрывается в той же строке, без отдельного окна. Отбор сообщений использует существующий `nagramiXCanPlayTemporaryVoiceInline`: доставленные голосовые облачной личной переписки, включая собственные и сохранённые временные копии. Секретные чаты, verification codes, незавершённые отправки, кружки и другие вложения нового маршрута не получают. Оба прежних ключа временных сообщений и их OR/default сохраняются. При OFF временная копия без TTL тоже не становится обычным допустимым вложением для ASR.

Для дополнительных способов нужны включённая расшифровка и выбранный пользователем provider. Apple, Whisper, Vosk, Cloudflare, Gemini, ChatGPT и Grok используют существующие настройки, разрешения, модели, ключи, согласие на сетевую обработку, ограничения размеров и локальный резерв. Авторасшифровка по-прежнему требует отдельного включения и обрабатывает только видимые загруженные входящие сообщения. Ручная обработка сохранённой копии также не запускает скачивание по удалённому серверному ID: нужны доступные локальные байты. При их отсутствии возвращается ошибка.

Штатная кнопка Telegram Premium доступна у живого одноразового сообщения, когда включены «Временные сообщения» и подтверждён Premium. Она сохраняет обычный запрос `messages.transcribeAudio`; наличие подписки, серверная доступность и результат определяются Telegram. В контекстном пункте выбранного Telegram provider дополнительно повторно проверяются настройки и живой объект перед RPC. Отказ сервера не подменяется другим provider, отправкой скрытой копии или заявлением об успешной расшифровке. Полностью удалённую с сервера локальную копию этот API расшифровать по старому ID не может: для неё доступны настроенные дополнительные способы. Реальный серверный ответ для одноразовых сообщений ещё не проверен.

## Сохранение механики

Плеер, playlist, маршрут открытия, native огонь/обратный отсчёт, вычисление сгорающей дорожки и guard подавления consumption не изменены. Подготовка ASR не использует воспроизведение или `AVAudioSession`. Для временной дорожки не включается обычный shimmer расшифровки, который мешал бы оформлению сгорания. Само появление текста не запускает таймер удаления и не записывает consumed/read attributes.

Новые методы TelegramEngine разрешают живой/видимый сохранённый объект без вызова открытия или `markTemporaryExpired`. Живой результат дополнительного способа записывается обычной локальной транзакцией и зеркалируется в уже существующую временную архивную запись. Архивный результат обновляет только эту запись и не воссоздаёт сообщение Postbox. Меняются только `AudioTranscriptionMessageAttribute` и `DerivedDataMessageAttribute`; исходный текст, entities, media, grouping, flags, дата и срок жизни сохраняются. Архивная очередь и повторные проверки настроек, отмены, исходного файла и более свежего текста не позволяют позднему распознавателю отменить очистку архива. Уже готовый текст, попавший в архив вместе со snapshot, можно раскрыть без нового серверного запроса и без повторного требования Premium.

Архивная схема получает необязательное поле `transcriptionAttributes`; прежний JSON читается без миграции/сброса. При рендере допускаются только два типа атрибутов ASR. Они сохраняются при повторном захвате того же вложения и удаляются вместе с записью при полной очистке. Для временной голосовой кеш опирается на неизменяемый Telegram file ID, размер и длительность: перенос байтов из облачного ресурса в локальный архив не обнуляет результат. Кеш обычных сообщений сохраняет прежнюю идентификацию ресурса и revision provider/model/language/credentials.

## Проверки

```sh
python3 scripts/validate_temporary_voice_transcription.py --source <native> --swiftc <swiftc>
```

Проверяются четыре полных output, 14 SHA guards и все Before/After templates до первой записи. Некорректные inputs/guards/templates и повторное применение отклоняются без частичной записи. В workflow новая проверка добавлена перед прежней цепочкой; старые validators обратимо снимают поздние стадии, сохраняя собственные SHA и прежние проверки.

Результат: по129 Swift-проверок в debug и optimized, 258 суммарно; 38 отказов некорректных overlay-входов без записи. Реальная композиция новой стадии и final upstream post-port на48 файлах совпала с независимым полным деревом; прежние иконки и локализация сохранены.

Swift в debug и optimized исполняет фактические Runtime/Settings/Coordinator, новые методы Engine/архива, Codable-схему и блок видимости кнопки. Speech/HTTP/Postbox, кодирование атрибутов, очередь/диск и UIKit представлены явными границами. Проверяются ON/OFF обоих старых ключей, обычные и сохранённые строки, native Premium и его отказ, все текущие дополнительные providers, кеш при смене ресурса, собственное сообщение, отсутствие байтов, замена файла, более свежий результат и очистка во время обработки. Внешние ASR-сервисы и пользовательское аудио при тестах не вызываются.

Дополнительно пройдены прежние проверки inline temporary voice, archive chat scope, consumption guard, standalone Vosk с настоящим C++ bridge и C API boundary, RU/EN локализация, Swift parse и TelegramCore import access. Незавершённые 69 языковых каталогов остаются отдельной задачей; разрешение на их внешнюю отправку не получено.

На iPhone необходимо проверить `→A` при воспроизведении/паузе, сохранение огня и прогресса, повторное прослушивание, входящее/собственное сообщение, выбранные способы с настоящими разрешениями/ключами, серверный результат Premium, возврат в чат и очистку во время ASR. Вторым аккаунтом проверить прежнее поведение consumption отдельно от чтения самой переписки. Исходные проверки не заменяют эти испытания.
