# Рассылка полного поста нескольким адресатам

Сборка **0.8.5/build165** и пакет проверены; физическая приёмка — device_pending. Публикация и точные подтверждения — [RELEASE_STATUS](RELEASE_STATUS.md).

Исправление после 0.8.4: `source_checked / native_compile_passed / device_pending`. Основание — видео пользователя: одна рассылка из защищённого канала в «Избранное» и Telegram. У первого адресата четыре элемента оставались в ожидании отправки, у второго появились восемь попарно повторяющихся фотографий без исходной подписи.

## Причина

`ChatControllerForwardMessages` один раз вызывал `nagramiXCopyMessagesAsNew`, затем передавал один результат каждому адресату. У копий совпадали localGroupingKey, локальные media/resource identities, временные пути и correlation IDs.

Нативный `PendingMessageManager.dataForPendingMessageGroup` собирает ожидающую группу по groupId среди всех messageContexts аккаунта, без фильтра peer. `sendGroupMessagesContent` выбирает peer по первому элементу. Поэтому две копии четырёх фотографий с одним localGroupingKey объединялись в группу из восьми сообщений разных адресатов. Состояние uploading одного из них также блокировало общую группу. Это конкретная воспроизведённая причина смешивания получателей; сам PendingMessageManager не менялся.

Дополнительно один uniquely referenced temporary path передавался нескольким отправкам, хотя штатный Fetch использует для такого ресурса move. Повторное использование перемещаемого файла нарушало владение ресурсом. Исправление разделяет и группы, и файлы, сохраняя исходный MediaBox-кеш.

## Изменение

- `NagramiXRecipientCopyBatch` подготавливает полный набор для каждого получателя до первого enqueue. Каждому принадлежат отдельные group IDs, локальные media/resource IDs, временные пути и correlation IDs. Файлы закрепляются hard link с прежним copy fallback; исходные байты загружаются существующим общим этапом подготовки.
- Содержимое каждого набора строит прежний реальный copier: текст/подпись, entities, custom emoji, спойлеры, порядок и группировка внутри набора сохраняются. RichText/InstantPage сохраняет собственные локальные embedded media каждого адресата. Применение шаблона тихой/отложенной отправки переносит только соответствующие send attributes, без подстановки файлов другого получателя.
- Все копии остаются uncommitted до начала enqueue. Ошибка подготовки любого адресата и отмена до enqueue освобождают все staging-файлы. Существующий одиночный copier по-прежнему сам передаёт владение native send; optional mediaCopy используется новым пакетным владельцем.
- После подготовки создаются и запускаются native enqueue signals всех адресатов одной операцией, без ожидания загрузки или доставки предыдущего адресата. Выбранные темы/reply targets, комментарий, fees и quiet/schedule/when-online применяются прежним commit-кодом.
- Подтверждение пересылки показывается после получения полного набора ненулевых local IDs от всех enqueue transactions. Отсутствующие IDs дают прежнюю локализованную ошибку. Enqueue подтверждает постановку в очередь, не доставку сервером; одинаковый момент сетевой доставки и атомарность нескольких серверных RPC не обещаются. Pending-наблюдение охватывает все копии и не перезаписывается последним адресатом.
- `take(1)`, guard повторного commit и одноразовый callback подготовки защищают от повторных эмиссий/позднего completion после отмены. «Свободный контент» повторно проверяется перед commit и после асинхронной проверки diversion.

Штатная серверная пересылка/репост сохраняет прежний путь. Права доступа и назначения, eligibility, paid/view-once исключения, сохранение/экспорт, настройки и локальный архив не расширяются. Рассылка не превращается в серверный forward защищённого оригинала.

## Стадия и доказательства

Поздний guarded stage `recipient_copy_isolation` после `free_content`, до post-port: три Swift-файла, 14 точных операций, девять guards. Оригинальные PendingMessageManager, EnqueueMessage, Fetch, media stager, eligibility и BUILD защищены hashes и не менялись. Все входы/шаблоны/якоря/выходы проверяются до первой записи. Новых зависимостей нет. Ранние canonical стадии, правки архива и «Свободный контент» сохранены.

`scripts/validate_recipient_copy_isolation.py --source <native> --swiftc <swiftc> --report <json>` исполняет настоящие copier, batch, file staging, pending group collector и новый блок агрегированного enqueue из UI. Foundation IO настоящее; Postbox/API, сигналы, доставка main queue и presentation — явные границы, не UIKit/серверная интеграция.

Результат: 63 сценария в debug и `-O`: четыре фотографии с подписью двум адресатам, независимые группы/ресурсы, блокировка только своего upload, перемещение файлов первым получателем, rollback при ошибке второго, отмена, файлы/смешанные сообщения/несколько альбомов, rich embedded media, комментарий, quiet/schedule/hide captions, старт обеих очередей до их ответа, отсутствие преждевременного подтверждения, повторные callbacks, все pending IDs и отказ при nil ID. Прежний реальный шаблон «один payload двум peer» воспроизводит группу из восьми; варианты с общими группой и путём отвергаются новыми проверками в обоих режимах. 18 прежних rich-post регрессий также проходят в debug/O. 35 некорректных входов отвергаются без частичной записи.

Свежая полная композиция Telegram 13.1.2 воспроизводит новую стадию и две предшествующие правки побайтно; конечный post-port сохраняет их, upstream PostboxImportCheck и Swift parse проходят. Обратное снятие стадии для предыдущих validators проверено. Артефакты сессии — `/tmp/nagramix-recipient-copy/verification.json`, `verification.log`, `composition.log`, `previous-stage.log`; временные файлы не считать постоянным архивом доказательств.

Apple SDK и пакет проверены в 0.8.5/build165; физическая приёмка ещё предстоит. На устройстве повторить исходное видео: защищённый канал → «Рассылка» → «Избранное» и второй чат; по четыре изображения и одна полная подпись каждому, без смешивания. Проверить разные скорости загрузки, холодный кеш, ошибку/отмену, комментарий/тему/тихо/расписание и обычную рассылку из открытого канала.
