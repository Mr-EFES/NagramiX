# YouTube: устойчивое разрешение системного PiP и фона

Стадия54 `youtube_playback_policy` следует за `edit_result_consistency`. Существующий общий переключатель PiP разрешает тот же системный WebKit PiP для YouTube, даже если страница повторно выставляет клиентский запрет. Плеер, HTML-video, позиция, поток и авторизация остаются исходными. Второй плеер или WebView не создаётся.

## Найденное расхождение

Стадия48 уже давала локальной включённой настройке приоритет над серверным `youtube_pip` и вызывала публичный `webkitSetPresentationMode` у существующего видео. Но `disablePictureInPicture` снимался только при входе. Страница могла снова установить свойство/атрибут или заменить элемент видео. Кроме того, скрипт видимости устанавливался после загрузки документа: обработчик сайта мог раньше сохранить настоящий getter и при уходе в фон поставить видео на паузу.

Предыдущий production-скрипт отдельно проходит реальный для него `probe → enter`. Затем страница возвращает запрет во время системного PiP; регрессионный fixture подтверждает, что запрет остаётся установленным. Это проверка поведения прежнего скрипта, а не его незнакомства с новой командой `policy`.

## Исправление

Скрипт устанавливается в начале документа во все фреймы существующей WKWebView. Native-мост передаёт область YouTube и разрешение, полученное от прежнего фонового владельца либо текущего запроса/PiP. Повторные одинаковые настройки не запускают обход DOM на каждом статусе проигрывателя. Открытый узел получает изменения общего checkbox через существующее уведомление; weak observer снимается при освобождении.

В разрешённой области сохраняются исходные свойства видео, снимается `disablepictureinpicture` и наблюдаются повторные изменения/замена видео. Используется захваченный в начале публичный метод WebKit, чтобы поздняя обёртка сайта не подменяла системный вход. Для вложенных iframe корректируется только директива `picture-in-picture` в `allow`; остальные разрешения сохраняются. Удалённые элементы освобождаются, а при OFF исходные свойства/атрибуты восстанавливаются с учётом замеченных изменений сайта. Отдельно проверен OFF во время PiP с последующим выходом.

Для уже играющего разрешённого видео ранние обработчики видимости не дают событию скрытия запустить остановку сайта. Фоновое аудио продолжает принадлежать прежним ManagedAudioSession и Now Playing. Нет автоматических `play`, `seek`, таймеров повторного старта или переноса URL потока. Пауза пользователя остаётся паузой; обычная потеря фокуса в видимом приложении сохраняет штатное поведение.

Самостоятельный сохранённый OFF фонового видео продолжает действовать так же, как для ролика без запрета. Активный системный PiP сохраняет аудио по прежнему правилу48. При OFF общего PiP сохраняется native/server-permitted путь; принудительное разрешение для YouTube снимается. Новых checkbox, ключей, строк или default нет. Обычные AVPlayer/HLS/sample-buffer плееры, права галереи, callbacks восстановления и аудиополитика вне WebEmbed закреплены19 точными guards.

## Проверки и границы

[Receipt](YOUTUBE_PLAYBACK_POLICY_CHECKS.json) содержит130 проверок настоящего Swift-моста и11 проверок production observer/реального Core-getter в debug и `-O` с warnings-as-errors; семь смысловых мутаций отвергаются в обоих режимах. Actual injected JavaScript исполняется в Node vm:72 проверки, четыре отвергнутые мутации и воспроизведённая регрессия предыдущей реализации. Проверяются повторный запрет, замена видео, исходные descriptors, iframe, native mode, отмена/stale callbacks, OFF, пауза и скрытие документа. WK/DOM границы представлены явными adapters.

Новая проверка входит в обязательный ранний gate до длинного overlay:20 полных fixtures/40 исполнений. Текущий полный helper обязан пройти настоящий AVKit/WebKit SDK typecheck на Apple; Linux явно сообщает `not_run`, не подменяя SDK doubles. Отдельный обязательный validator работает после применения54. Общие557 Swift parse, inverse787 путей/279 отрицательных случаев, migration/Postbox/member audits и строгие71×650 каталоги прошли.

Реальная сеть YouTube, звук/блокировка телефона, WebKit scheduling и плавность системной анимации на iPhone здесь не проверялись. Клиентские hints не равнозначны гарантии воспроизведения недоступного потока, DRM или режима, отвергнутого самим WebKit/iOS. При неподтверждённом старте остаётся прежний timeout и восстановление галереи; ложного состояния активного PiP нет.
