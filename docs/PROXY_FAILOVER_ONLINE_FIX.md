# Автопереключение прокси: приоритет основного соединения

20 октября пользователь разрешил исправить **только пункт1** [проверки стабильности](STABILITY_REVIEW_2026-10-20.md). Реализовано в `main`, без SDK/Actions/IPA/commit/push. Следующие ошибки первого входа, прочтений тем и записи архива остаются отдельными задачами.

## Исправление

В `NagramiXProxyFailoverController.needsConnection` штатный `.online` теперь означает отсутствие причины для автоматического переключения. Удалён локальный снимок `healthStatuses`, который раньше требовал положительного независимого ping даже при ONLINE. Проверочный сокет может не открыться, пока уже установленное основное соединение работает; его ошибка больше не запускает разрыв работающего соединения.

Монитор доступности остаётся прежним. Во время `.connecting`/`.updating` по истечении выбранного срока выбирается только проверенный доступный резерв. При отсутствии резерва сохраняется текущий сервер и ожидается результат ограниченного фонового проверяющего. `.waitingForNetwork`, выключенная автоматика/прокси, VPN bypass и фон отменяют переключение. Полученный ONLINE отменяет таймер, ожидание резерва и ещё не применённую автоматическую транзакцию.

Начальные ON/30секунд, пользовательские OFF/15/30/60, список серверов, активный сервер, настройки звонков/DNS/IPv6/VPN и UI не меняются этой правкой. С одним уникальным сервером переключения нет. События проверки резерва не перезапускают срок основного соединения. Прежние поколения таймеров, cancellation flag и проверки полного `ProxyServerSettings` в транзакции сохранены побайтно.

## Смена сервера и порядок событий

Не следует идентифицировать соединение только по строке `proxyAddress`: она не содержит порт, тип подключения или credentials. ONLINE, полученный во время смены настройки, сам по себе не разрешает автоматически выбрать другой сервер. Ручная настройка продолжает применяться штатным сетевым слоем; если новое соединение не установлено, последующие native connecting/updating события запускают срок восстановления.

По Git-blob-проверенным исходникам закреплённого Telegram13.0:

- `Network.updateProxySettings` сравнивает настройки транспорта, при изменении сбрасывает connection status и обновляет API environment;
- `MTProto.contextApiEnvironmentUpdated` сбрасывает транспорт при смене proxy settings;
- `MTProto.transportConnectionStateChanged` отвергает callback, если `transport != _transport`.

Эта правка не заменяет native transport lifecycle и не добавляет новый RPC, принудительный reconnect или параллельный сокет. Ручной выбор и отложенные автоматические записи по-прежнему защищены полным сравнением сервера и поколением. Если основное соединение восстановилось до выполнения queued transaction, production cancellation guard возвращает текущие настройки без автоматической записи.

## Проверено

`scripts/validate_proxy_failover.py` принимает before/after полного generated overlay и Swift compiler. Проверяется равенство множеств файлов и ровно одно изменение — canonical `Network/NagramiXProxyFailoverController.swift`. Обратная замена только ONLINE-ветки и удалённого ping-снимка побайтно восстанавливает предыдущий контроллер, включая прежние defaults и guards. Остальные415из416выходных файлов неизменны.

Настоящий контроллер целиком и настоящий `NagramiXProxyPreferences` выполняются в debug/optimized с warnings-as-errors. `NagramiXProxyFailoverBoundary.swift` заменяет только очереди/время/сигналы/DTO/сетевые события/AccountManager и монитор. `NagramiXProxyFailoverTests.swift`: **87проверок на каждый режим**,0отказов. Старый контроллер в обоих режимах не проходит отдельный regression-only сценарий с ONLINE и неудачным ping.

Проверены:

- ONLINE с отсутствующим, ожидающим, неудачным и успешным ping; другой/отсутствующий адрес в метке статуса не вызывает разрыв ONLINE;
- настоящие connecting/updating события, исходные сроки15/30/60, повторные события без перезапуска срока, отсутствие раннего переключения;
- восстановление до дедлайна, отменённый timer callback, восстановление во время queued transaction, доступный резерв и повторный отказ резерва;
- отсутствие доступного резерва и его появление позже; один сервер и дубликаты списка;
- ручной выбор, включая одинаковый hostname с другим портом/credentials; последующая неудача ручного соединения всё ещё запускает failover;
- удаление резерва, OFF автоматики/прокси, VPN bypass, фон, отсутствие сети и stop с уже поставленной в очередь транзакцией;
- возобновление после OFF/VPN/фона/возврата сети, изменение срока, сохранение IPv6 и настройки звонков, отсутствие сброса срока от соседнего checkbox.
