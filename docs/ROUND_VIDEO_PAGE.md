## Интерфейс и сохранение

В «Прочее» после загрузки отдельная группа «Качественные кружки». Переключатель по умолчанию OFF, после включения появляется disclosure «Настройка кружков» с выбранным уровнем. Stable IDs5000/5001 и сохранённые ключи прежние. Новый header5002, отдельная секция добавлена в конец enum, прежние raw values не сдвигаются.

Disclosure делает push самостоятельного ViewController с обычной кнопкой назад. Четыре группы: качество, частота кадров, кодек, киноэффект. Кодеки H.264 (AVC)/«Стандартное сжатие» и H.265 (HEVC)/«Эффективное сжатие». Названия уровней: Стандарт, Высокое, Максимум. Нет слайдера битрейта, modal close, bottom-sheet handle или отдельной кнопки применения.

Выбор сохраняется сразу; «Назад» возвращает в Прочее с теми же настройками. Существующие видимые UITableViewCell обновляются без анимации, reloadData/reloadRows/setItemGroups не используются, offset и сам экран не пересоздаются. Поддержка Cinematic кэшируется при создании страницы, а не сканируется при обновлении каждой галочки. На реальном UIKit плавность ещё не проверена.

## Параметры реальной записи

| Уровень | Размер | Целевой битрейт видео |
| --- | --- | --- |
| Стандарт | 480×480 | 1,2 Мбит/с |
| Высокое | 512×512 | 1,5 Мбит/с |
| Максимум | 640×640 | 1,7 Мбит/с |

30/60FPS и выбранный H.264/H.265 сохраняются. Значения модели одинаковы в Camera и NagramiXMediaSettings, writer уже использует quality.bitRate. Deferred/trim export также обновлён, OFF штатный. Битрейт — средний целевой, фактический размер зависит от кадров, аудио, контейнера и encoder. Нельзя обещать файл12МБ:1,7Мбит/с×60с/8=12,75МБ только видео, без аудио.

## Киноэффект

Предыдущий UI оценивал ON по выбранным60FPS и поэтому показывал недоступность устройства, даже когда Cinematic30 поддерживается. По [Apple](https://developer.apple.com/videos/play/wwdc2025/319/) исходные Cinematic-форматы поддерживают30FPS, а [videoFrameRateRangeForCinematicVideo](https://developer.apple.com/documentation/avfoundation/avcapturedevice/format/videoframeraterangeforcinematicvideo) описывает реальный диапазон каждого формата.

Новый UI разрешает ON, если доступна текущая конфигурация либо тот же уровень при30FPS. Во втором случае диалог предлагает явно перейти на30FPS и включить эффект. «Отмена» не меняет настройки. Без поддержки обоих вариантов ON недоступен. Пока эффект включён, несовместимые FPS/качества недоступны; OFF доступен всегда.

Capability helper перебирает фактические форматы всех подходящих устройств: спереди TrueDepth/Wide Angle, сзади Dual Wide/Triple/Wide Angle. Выбирает первый совместимый источник и его самый маленький подходящий формат. Снято искусственное ограничение1920по длинной стороне: поддерживаемый4Kисточник можно уменьшить до выбранного кружка. Проверки Cinematic/NV12/минимальной стороны/FPS/обеих камер сохранены. Реальная CameraNeo выбирает устройство тем же методом с тем же snapshot настроек. Runtime input support проверяется до enable, неверный input не включается; обычная камера и ручной focus при активном эффекте не менялись.

Это исправление проверки конфигурации, не аппаратное доказательство работы Cinematic на конкретном iPhone17ProMax/iOS27. Реальные bokeh/нагрузка/FPS требуют приёмки.

## Длинные HEVC и квадратные сообщения

В [схеме Telegram](https://core.telegram.org/constructor/documentAttributeVideo) тип кружка задаётся round_message, кодеки имеют идентификаторы h264/h265. В исследованном пути клиента нет смены типа по45секундам или12МБ. TransformOutgoingMessageMedia сохраняет attributes при обновлении размера/thumbnail, API mapper сохраняет round-флаг. Доказательств универсального серверного лимита12МБ не найдено; не подменять этим диагноз.

Новый этап сохраняет instantRoundVideo и явно записывает выбранный codec.telegramIdentifier для записей с включённой функцией. OFF оставляет nil как прежде. Добавлен обезличенный журнал подготовки: длительность, размер исходного файла, кодек и число сегментов; это не размер конечного deferred upload. Нет скрытого пересжатия до выдуманного лимита, отправки обычным документом или локальной подмены полученного от сервера типа.

Исходящие round/codec metadata и фактический API flags mapper проверены для60сочетаний10–60секунд. Это не серверная отправка. Причина показанного квадрата с белыми углами не воспроизведена по одному скриншоту и не объявляется окончательно устранённой снижением битрейта. Нужен реальный минутный HEVC и проверка возвращённых сервером attributes/received file в следующем IPA.
