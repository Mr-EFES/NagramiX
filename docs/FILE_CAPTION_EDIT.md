# Одинаковое оформление файла при отправке и редактировании

Уточнение пользователя по второму сообщению на скриншоте: верхний край файла почти касается границы расширенного пузырька, хотя зазор до текста снизу есть. Требуется классическая ширина пузырька и одинаковый отступ сверху и под файлом, в том числе при сохранении из обычного и расширенного редакторов.

Предыдущий ответ о15pt относился только к штатному file renderer. Это не доказывало вид rich-сообщения в другом клиенте. Стадия97 исправила создание совместимых постов из отдельного редактора, но не меняла общий обработчик редактирования.

## Причина и изменение

В `ChatControllerLoadDisplayNode.swift` edit callback выбирал rich по `content.isEntityExpressible()`. Этот метод всегда отвергает media-блок. Поэтому даже представимый одиночный файл с подписью при редактировании rich-документа снова получал rich payload. Обе формы editor сходятся в этот callback, но новый native caption selector97 там не использовался.

Стадия98 `file_caption_edit` после97 меняет два runtime-файла:

- `ChatControllerLoadDisplayNode.swift`: helper использует прежний `nagramiXComposerCaptionFiles`, действующий account caption limit и допускает ровно один обычный файл. Такой edit передаёт файл через штатный `RequestEditMessageMedia.update`, текст/entities — через прежний pending manager, без rich attribute. Сохраняются message ID, caption, file reference, права, очередь, ошибки и обработка ответа. Явно выбранная замена файла имеет прежний приоритет. Карточка URL не подменяет файл.
- `ChatMessageFileBubbleContentNode.swift`: полный промежуток под файлом складывается из bottomInset файла и topInset следующего text node. У file node сосед имеет тип `.text`, поэтому text node вычитает2pt из своего обычного topInset. Новый минимум учитывает это вычитание: `file.top - max(0, text.top - 2)`. В проверенных штатных константах полный зазор получается15pt, как и сверху файла. Ширина и положение файла по горизонтали не меняются; высота учитывает зазор.

Файл без подписи также допускается. Обычное редактирование подписи без media-блока сохраняет `.keep`. Частичный исходный rich-документ или наличие отдельной full-page версии блокируют автоматический переход, поскольку прежний edit seed может содержать только сокращённую страницу. Несколько файлов, inline-расположение между текстовыми областями, сложные структуры и подпись за пределами лимита сохраняют прежний rich-путь. Голосовые и кружки не переводятся на новый editMedia путь. Код RPC, upload, pending manager, преобразования текста/entities, оплаты и callbacks самого расширенного экрана не меняется.

В NagramiX прежняя стадия80 уже даёт ведущему rich audio/document верхний отступ15pt в host/preview. Она сохраняется и повторно проверяется. Штатный Telegram не получает локальные layout-правки NagramiX: на него влияет выбор штатного file-caption payload, а своё оформление он рисует самостоятельно. Точное равенство пикселей и принятие сервером преобразования ранее отправленного rich-сообщения требуют live-проверки после сборки.

## Проверки и ограничения

[Результаты](FILE_CAPTION_EDIT_CHECKS.json). Swift fixtures исполняют реальные Document/model converters, caption eligibility, новый helper, обе production ветки решения edit/rich и выбора media. Проверяют оба editor-state пути, MP3/document/video, полный текст, named URL/bold, file identity, явную замену, account limit, file-only, caption-only, несколько файлов, inline media и исключения voice/round. Аккаунт/платформенный UI/opaque rich page представлены явными IO-границами. Сеть и pending manager не симулируются как успешная доставка.

Отдельная геометрия выполняет настоящие compact file/text constants и production switch top/bottom. Проверяет равенство полного зазора, прежнюю ширину/верхний inset, включение зазора в высоту и неизменность no-caption/bubbleless вариантов. Прежний rich V2 sequence/spacing/audio/document/header fixture выполняется без изменения его кода. Смысловые мутации rich-on-edit, потери файла, частичного edit и неравного зазора обязаны отклоняться в debug и `-O`.

Новый checker обязателен в начале macOS preflight и после применения98. На macOS geometry typecheck использует настоящий UIKit; Linux помечает его `not_run`. Эти проверки не заменяют полную Apple SDK-компиляцию, iPhone или штатный клиент.

Новая IPA этой задачей не собирается. `composer_file_attachments` уже `compile_pending`, все проверки на телефоне `device_pending`. После новой сборки проверить новый пост и редактирование существующего совместимого rich-поста через обе формы editor, MP3/документ/видео, пустую подпись, ссылку с названием, ответ, замену файла, поворот и темы. Сравнить верхний/нижний зазор и ширину в NagramiX и штатном Telegram; проверить реальный серверный ответ и отсутствие потери файла/стилей. Без редактирования старые серверные rich-посты не переписываются.

Новых строк, настроек, зависимостей и изменений подписи нет. Прежние snapshots/plans, README/LICENSE, аннотации и опубликованные релизы/файлы/теги сохраняются. Веб-плеер и другие несвязанные функции не меняются.
