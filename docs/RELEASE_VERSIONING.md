## Аккаунт сборки и публикации

Коммиты оформляются как `Mr_EFES` с привязанной noreply-почтой владельца; логин GitHub — `Mr-EFES`. Перед запуском Actions проверить `gh api user --jq .login`. Actor и triggering_actor сборки должны быть `Mr-EFES`.

При `publish_release=true` Actions собирает и проверяет IPA, но не создаёт GitHub Release через служебный токен. После успешной проверки агент скачивает неизменённый ZIP исходного Actions-артефакта и завершает разрешённую публикацию из checkout выбранной версии:

```sh
python3 scripts/publish_owner_release.py --source-run-id <ID_исходной_сборки> --artifact-zip <скачанный_ZIP>
```

Обычный релиз используется по умолчанию; `--prerelease` добавляется только для согласованного тестового выпуска. Скрипт требует личную авторизацию `gh` как `Mr-EFES`, успешный build и холодный gate, сверяет ZIP с digest GitHub, пакет и provenance. Черновик, финальная публикация и все три release assets создаются этим аккаунтом. Автор и uploader проверяются до открытия релиза; опубликованные релизы и непустые черновики не заменяются. Если три исходных файла загружены владельцем через браузер, явный режим `--finalize-uploaded` проверяет полный набор, размеры/SHA256, source и каждого uploader и завершает собственный черновик без загрузки или перезаписи файлов. Неполный или изменённый набор отклоняется до записи. Новых секретов репозитория для этого порядка не требуется. Если CLI не скачивает Actions ZIP, агент использует подключённый GitHub artifact tool и передаёт исходный файл скрипту.

После повторной авторизации CLI профиль выбирать только для команды публикации: `env -u GH_TOKEN GH_CONFIG_DIR=<подтверждённый_профиль_gh> python3 scripts/publish_owner_release.py ...`. Иначе runtime GH_TOKEN имеет приоритет над сохранённым входом и прежний401 может повториться. Содержимое токенов и credential-файлов не читать, не выводить и не коммитить. Аккаунт проверяется скриптом до любых записей.

Проверка подготовки без запуска SDK и публикации: `python3 scripts/validate_owner_publication.py`. Изменение этого порядка не разрешает новую сборку само по себе.

До 1.0 последний разряд принимает значения 0–9, затем переносится в следующий разряд. После 1.0 пользователь задал запись 1.1 и далее; перед этим переходом требуется адаптировать валидатор формата из трёх компонентов.

Правило само по себе не разрешает сборку или публикацию. По отдельной команде на следующий выпуск синхронно обновить workflow, registry, handoff, статус и единственную текущую аннотацию в `product/releases/`. README сохранять без изменений. Опубликованный IPA, его checksums и provenance не заменять задним числом.

По прямому указанию пользователя история свёрнута до корневого коммита 0.8.4, тег перенесён на эту базу, сам IPA сохранён. Это разовая очистка, не разрешение на дальнейшую перезапись истории или удаление релизов.
