# Восстановление связи до и после первого входа

После134исправлено восстановление foreground при повторном запуске failover: [актуальная правка](RECOVERY_STORAGE_FIXES.md).

20 октября исправлен пункт2 [проверки стабильности](STABILITY_REVIEW_2026-10-20.md). Правка исходников в `main`, без новой версии, SDK, Actions или IPA. Статус: **source_checked / native_compile_pending / device_pending**.

Раньше `UnauthorizedAccount` применял выбранный прокси и VPN bypass штатным наблюдателем, но наш DNS/IPv6 reconnect и автоматический выбор резервного прокси подключались только в авторизованном `Account`. Теперь оба используют один [NagramiXNetworkRecovery](../ios/Sources/TelegramCore/NagramiXNetworkRecovery.swift). Пользовательские настройки и их значения по умолчанию сохранены.

## Поведение и владение

- До авторизации смена DNS/IPv6 вызывает переподключение основной сессии. При включённой автоматике недоступный прокси может смениться на проверенный резерв через сохранённый интервал15/30/60секунд; без сохранённого выбора30секунд. Один сервер, выключенная автоматика, VPN bypass и отсутствие маршрута сохраняют прежние ограничения.
- Запуск и остановка монитора следуют штатному `Network.shouldKeepConnection`. Принудительного удержания сети для восстановления нет. DNS reconnect читает последнее применённое состояние на самой сетевой очереди: приостановленная сессия остаётся приостановленной.
- Смена дата-центра и переход после авторизации создают нового владельца для каталога аккаунта. Предыдущий немедленно теряет право на DNS reconnect и запись нового прокси, даже если старый `UnauthorizedAccount` ещё удерживается вызывающим кодом. Остановка подписок/монитора/таймеров завершается на очередях. Нативные завершающие запросы старой сети насильно не прерываются.
- Отложенная транзакция проверяет право владельца непосредственно перед изменением сохранённого прокси. Одного асинхронного `stop()` для этого недостаточно. Позднее освобождение старого владельца не удаляет нового; callback DNS также повторно проверяет владельца на сетевой очереди.
- Supplementary/extension-сети получают DNS reconnect, но не запускают автоматику выбора прокси. Разные каталоги аккаунтов и роли не отменяют чужие обработчики. Существующий общий арбитраж failover сохранён.
- Уже открытый Postbox передаётся после первого входа по прежним проверкам id/rootPath/basePath/test environment и только для основного процесса. Авторизация, ключи, код входа, база, WEB carrier, actual resolver, IPv6 policy и UI не переделаны.

## Приёмка после отдельно разрешённой сборки

1. На первом входе без авторизованного аккаунта добавить недоступный основной и доступный резервный прокси. Проверить автопереход через30секунд, затем сохранённые15/60; с выключенной автоматикой и одним сервером перехода нет.
2. До входа поменять DNS и IPv6, проверить новое соединение без перезапуска. Проверить реальные AAAA/IPv4 fallback и SOCKS5/MTProto/WEB, VPN bypass, Wi-Fi/LTE и потерю маршрута.
3. Выполнить вход со сменой дата-центра. Проверить переход к чатам без повторного открытия/миграции Postbox; повторить при недоступном прокси и переключении сети.
4. После входа повторить DNS/IPv6 и failover, фон/возврат, несколько аккаунтов, ручной выбор во время таймера. Убедиться, что старые сессии не возвращают прежний выбор и не создают лишних переключений ONLINE.
