# Зазор под файлом в подписи сообщения для разных клиентов

Стадия109 `file_caption_wire_spacing`, после108 `round_quality_horizontal_page`.

Владелец показал один пост с MP3 в NagramiX и официальном Telegram. Прежние97/98 увеличивали зазор только локальной отрисовкой NagramiX; в данные сообщения он не входил. После объяснения ограничений протокола и эскиза владелец разрешил добавлять пустую строку в саму подпись. Это новое явное разрешение на изменение текста подписи; ширину и классический тип пузырька менять не требуется.

## Данные отправки и редактирования

Обычный и отдельный расширенный редакторы продолжают использовать прежний native file/caption путь. После штатных Markdown conversion, trim и split новый общий `chatComposerSpacedFileCaption` добавляет ровно один `\n` перед непустой подписью обычного документа или аудиофайла. Пустая строка находится в поле текста сообщения и передаётся другим клиентам вместе с файлом.

Перенос добавляется после trim: штатный `trimChatInputText` удаляет начальные пустые строки, поэтому вставка раньше обработки не работала бы. Стили NSAttributedString сохраняются. При новой отправке все entities сдвигаются на фактическую добавленную UTF16-длину; URL, жирное выделение, подчёркивание, упоминания и другие существующие типы не заменяются. При edit генерация entities выполняется после добавления строки.

В `ChatControllerNode` и делегирующем helper отдельного редактора передаётся действующий account caption limit, ограниченный прежними4096. Строка занимает один UTF16-символ. Если исходная подпись уже исчерпала лимит, она сохраняется целиком без дополнительного переноса: текст не обрезается и новый слишком длинный запрос не создаётся. Файл без подписи сохраняет пустой текст. В группе файлов подпись, как и прежде, прикреплена только к последнему файлу. Порядок, reply/thread, grouping, file reference, байты медиа, inline stickers и обычная/тихая/отложенная отправка сохраняются.

Голосовые сообщения, кружки, видео, анимации и стикеры не получают эту строку. Фото и текст без файла также остаются прежними. Сложные rich-документы и подписи за пределами native caption eligibility сохраняют прежний rich fallback. Новый формат не переписывает уже отправленные сообщения автоматически. Он применяется к новым совместимым отправкам и при последующем сохранении подходящего сообщения через редакторы NagramiX. Уже отправленный пост нужно открыть на редактирование и сохранить заново.

Общий edit callback учитывает явную замену медиа раньше старого файла. Замена файла фотографией/видео не наследует строку от прежнего MP3. Для подписи над медиа и rich payload строка не добавляется. Native trim и идемпотентный helper предотвращают накопление переносов при повторных сохранениях. Права, premium emoji gate, выбор editMedia, pending manager/RPC, ошибки и завершение edit остаются прежними.

## Отображение

У нового file-caption с сохранённой строкой FileBubbleContentNode использует штатный отступ под файлом вместо добавки97/98. Это предотвращает двойной зазор в NagramiX. При ожидающем edit учитывается `item.attributes.updatingMedia.text`, как и в соседнем text node, чтобы локальная компоновка соответствовала показываемой подписи. Для старых сообщений без строки прежний локальный зазор сохраняется.

Верхний отступ файла, горизонтальные размеры и ширина пузырька не менялись. В обычной compact-конфигурации file top остаётся15pt. Нижний промежуток теперь складывается из native file/text insets и высоты пустой строки. Его фактическая высота зависит от шрифта и renderer; равенство старым15pt не обещается. Официальный Telegram сам определяет внутренние отступы и отображение текста. Пиксельное совпадение клиентов по эскизу не считается проверенным.

В исходниках нижележащие enqueue/store/sendMedia/editMessage передают текст без дополнительного trim, а pinned native text node берёт `message.text` напрямую. Это подтверждает путь данных в коде, но не заменяет live-проверку сервера и двух приложений. Изменение поста через другой клиент впоследствии может снова удалить начальную строку его собственным trim.
