# Надёжность прокси и DNS/DoH

Исправления сохранены для 0.4.5. Пользователь сообщил работу прокси в предыдущем IPA; нативная компиляция сохранённого кода прошла в сборке 0.4.5 №73, повторная проверка ожидается.

## Выбор и включение

Включение «Использовать прокси» и нажатие любой строки сохранённого прокси включают использование и автопереключение. Пользователь может вручную отключить автоматику; следующее нажатие строки включает её снова. Редактирование и просмотр сведений не меняют переключатели.

## Таймер и резервные серверы

Контроллер работает в жизненном цикле аккаунта. Статусы connecting и updating, которые UI показывает как «Соединение», запускают единый срок 15/30/60 секунд. Повторные события и переходы между ними не сбрасывают таймер. Online другого proxyAddress, включая старое прямое соединение, не считается успехом выбранного прокси. MTProto сообщает в proxyAddress поле ip, поэтому сопоставление производится по host; одинаковый host с разными портами этим статусом не различается.

На дедлайне пинг зависшего активного сервера сбрасывается. Выбирается следующий по циклическому порядку сервер с успешной штатной проверкой MTProxyConnectivity не старше 180 секунд. Дубликаты исключены. Подключение к непроверенным/недоступным серверам и дополнительные последовательные 12-секундные probes из failover удалены. Смена activeServer начинается на дедлайне; завершение сетевого handshake не гарантируется к 16-й секунде. Если свежего резерва нет, выбор сохраняется и ожидается результат общего ограниченного checker.

Пинг подтверждает проверку обмена с Telegram, но не полноценную работу аккаунта. Каждый выбранный резерв имеет своё окно 15/30/60 до online; неудачный сбрасывается и выполняется новый выбор. Автоматический возврат на непроверенный исходный сервер удалён. При отсутствии физической сети таймер отменяется, текущий выбор остаётся прежним.

Поколение операции и условия транзакции защищают ручной выбор, удаление кандидата, выключение прокси/автоматики и смену таймера. Кэш общий с UI через Atomic в Network. В журнал пишутся события запуска/истечения срока и выбора резерва без адресов и credentials.

## Проверка списка и нагрузка

Максимум две штатные проверки на checker аккаунта, каждая не дольше 12 секунд. При успешном соединении новый проход через 120 секунд после предыдущего, при восстановлении — через 30. Запрос обновления из failover не отменяет уже идущий проход и ограничен 30-секундным интервалом начала. Свежесть успешного результата ограничена 180 секундами; для очень длинных списков старые пинги могут устаревать до завершения следующего полного прохода.

Периодические проверки не запускаются при выключенных прокси, отсутствии сети и после уведомления UIKit об уходе в фон. При возвращении список обновляется. Ручная кнопка «Проверить все» запускает немедленный ограниченный проход, даже при выключенном использовании, отображает состояние проверки, пинги и итог. Отмена и идентификаторы probe защищают от устаревших callback. Нефинитный/отрицательный RTT отклоняется, чтобы вывод пинга не приводил к ошибке преобразования в Int.

Пауза приложения iOS не позволяет обещать точное срабатывание таймера в фоне. Нагрузка и расход батареи требуют измерения на устройстве; нулевой расход не обещается. Несколько аккаунтов имеют собственные checker, тестировать суммарную нагрузку отдельно.

## DNS/DoH

Системный DNS использует штатный асинхронный resolver. Для Google, Quad9, AdGuard, Mullvad, Cloudflare и пользовательского endpoint выполняются RFC 8484 GET-запросы A/AAAA; POST оставлен резервом для endpoint, которым он необходим. HTTPS и проверка сертификата обязательны. При GET сохраняются параметры пользовательского URL, параметр `dns` заменяется сформированным запросом.

`NSURLSession` выполняет запрос вне UI thread. Request/resource timeout — 8/12 секунд; вызов через `MTDNS` имеет общий предел 12 секунд. После ошибки или таймаута `MTDNS` переходит к штатному native resolver, поэтому недоступный DoH не удерживает соединение бесконечно. Это означает возможное использование системного DNS при отказе выбранного провайдера.

Отмена, обращение к текущему запросу и callback защищены одним рекурсивным `@synchronized`. Следующая попытка копирует блок под тем же замком и проверяет его перед вызовом: прежний код допускал вызов nil-блока при конкурентной отмене. DNS-парсер ограничивает длину сообщения/имени, проверяет границы указателей сжатия, усечение, opcode и код ошибки. Неправильные ответы завершаются ошибкой и резервным разрешением имени.

## Выполненные проверки

Полный feature overlay применён к закреплённым исходникам Telegram-iOS. Проверены синтаксические деревья изменённых Swift и Objective-C (это не typecheck/компиляция), Python syntax, метаданные и whitespace.

2026-10-04 `scripts/check_doh_providers.py` отправил настоящие DNS A/AAAA из Cloud:

| Провайдер | GET | POST |
| --- | --- | --- |
| Google | успешно | успешно |
| AdGuard | успешно | успешно |
| Mullvad | успешно | HTTP 400 |
| Cloudflare | успешно | HTTP 400 |
| Quad9 | HTTP 503 шлюза Cloud, connection timeout | HTTP 503 шлюза Cloud, connection timeout |

Эти результаты проверяют доступность endpoint из Cloud. Они не доказывают работоспособность iOS-resolver, Quad9 из сети пользователя или отсутствие всех возможных крашей. Пользовательский DoH неизвестен и проверяется приложением при сохранении. Для сообщения о прежнем сбое DNS нет crash/ANR stack trace.

## Обязательная проверка после сборки на iPhone

1. Для каждого таймера 15/30/60 выбрать сервер, который пингуется, но не соединяет аккаунт, при наличии рабочего резерва. Проверить переход по истечении окна, в том числе при `.connecting` без флага проблем, `.updating`, переходах и повторных событиях статуса.
2. Проверить пингующийся, но не достигающий `.online` резерв, недоступные и повторяющиеся серверы, отсутствие рабочего резерва, возврат доступности после следующего прохода без выбора непроверенного адреса.
3. Проверить ручной выбор и выключение использования/автоматики перед дедлайном, удаление кандидата, смену таймера, закрытие настроек, несколько аккаунтов, выход из аккаунта.
4. Проверить кнопку «Проверить все», фоновые проходы при закрытом экране, длинный список и отсутствие накопления запросов/таймеров. Периодические проходы относятся к работающему приложению: iOS может приостановить его в фоне.
5. Для системного DNS и всех DoH проверить холодный запуск, повторный запуск, смену провайдера, плохой URL, HTTP-ошибку, таймаут, отмену во время ответа, резервный native DNS.
6. Проверить потерю/возврат сети, переход Wi-Fi ↔ мобильная сеть, паузу/возврат приложения. При краше сохранить журнал iOS с трассировкой.

Успех выбранного прокси — online с его host и успешный результат checker. Если актуальная проверка даёт notAvailable, прежний online не удерживает автоматику. Выбранный сервер проверяется первым (максимум 12 секунд на probe, меньше минимального таймера 15), в том числе после ручной смены; повторные статусы без смены сервера этот проход не перезапускают.

Уход в фон отменяет также таймер failover, на возврате начинается новое окно. Ручной тап строки публикует отдельный сигнал отмены, включая выбор уже активного сервера. Захваченный Atomic-флаг отмены проверяется внутри транзакции переключения, чтобы callback прежнего поколения не отменял ручной выбор или действие после паузы.
