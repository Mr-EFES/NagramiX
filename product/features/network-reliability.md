# Надёжность прокси и DNS/DoH

Изменения включены в исходники версии 0.4.0. Нативная компиляция и проверка на iPhone ещё не выполнены.

## Выбор и включение

Включение «Использовать прокси» на экране прокси включает автопереключение. Его можно вручную отключить, не выключая использование прокси. Следующее включение использования снова включает автоматику. Если активного сервера нет, выбирается первый сохранённый.

Нажатие строки сохранённого прокси выбирает его и включает использование, включая случай, когда выбранный ранее сервер был выключен. Если прокси уже используется, ручной выбор другого сервера сохраняет ручное выключение автоматики. Просмотр сведений и редактирование остаются отдельными действиями.

## Таймер и резервные серверы

`NagramiXProxyFailoverController` работает от `Network.connectionStatus` в жизненном цикле аккаунта. Таймер 15/30/60 секунд начинается при `.connecting`, независимо от запаздывающего флага проблем прокси. Повторные события `.connecting`, включая изменение этого флага, не сбрасывают таймер.

По истечении окна выбирается следующий по порядку сервер со свежим успешным результатом штатного `MTProxyConnectivity` (не старше 90 секунд). Если свежих резервов нет, кандидаты проверяются штатным механизмом с ограничением 12 секунд на проверку. Это дополнительное время требуется при отсутствии заранее проверенного резерва. Обход начинается после выбранного сервера и продолжается с начала списка; дубликаты исключены.

Успешный пинг проверяет обмен с Telegram через прокси, но не гарантирует полноценную работу аккаунта. После переключения кандидат должен достигнуть настоящего `.online` в выбранное окно 15/30/60 секунд. Если этого не случилось, его результат доступности сбрасывается и выбирается следующий резерв. При исчерпании кандидатов возвращается первоначальный выбор; новые результаты периодической проверки позволяют возобновить попытки.

Каждый таймер, проверка и callback проверяет поколение операции. Ручная смена прокси, изменение списка, выключение использования/автоматики и восстановление соединения отменяют устаревшие действия. Транзакция смены дополнительно проверяет включённость автоматики, использования, прежний активный сервер и наличие кандидата в списке. При `.waitingForNetwork` перебор прекращается: смена прокси не устраняет отсутствие физической сети.

## Проверка списка без открытия настроек

Используется существующий `ProxyServersStatuses`, общий для контроллера аккаунта и экрана прокси; второго независимого списка результатов нет. Его ссылка в `Network` защищена `Atomic`.

- В проверяющем списке одновременно выполняются максимум две штатные проверки прокси; каждая завершается результатом или таймаутом за 12 секунд. При отсутствии свежих резервов контроллер переключения может дополнительно проверять одного кандидата; его результат возвращается в общий список.
- При включённом использовании и доступной сети новый проход начинается через 60 секунд после завершения предыдущего. Для длинных списков полный проход занимает больше минуты, но параллелизм не растёт.
- Фоновое обновление сохраняет предыдущие результаты до новых ответов; автопереключение учитывает срок их актуальности.
- «Проверить все» запускает немедленный проход с отображением проверки и штатным итогом. Во время отсутствия сети возвращаются недоступные результаты.
- Удаление/повторная проверка серверов отменяет старые запросы; идентификаторы проверок защищают результаты от устаревших callback.
- Выключение использования прекращает периодические проходы. Остановка аккаунта отменяет проверки и таймеры.

Пинг и автоматика уменьшают время восстановления, но не могут гарантировать незаметное переключение при потере сети или отсутствии доступных серверов.

## DNS/DoH

Системный DNS использует штатный асинхронный resolver. Для Google, Quad9, AdGuard, Mullvad, Cloudflare и пользовательского endpoint выполняются RFC 8484 GET-запросы A/AAAA; POST оставлен резервом для endpoint, которым он необходим. HTTPS и проверка сертификата обязательны. При GET сохраняются параметры пользовательского URL, параметр `dns` заменяется сформированным запросом.

`NSURLSession` выполняет запрос вне UI thread. Request/resource timeout — 8/12 секунд; вызов через `MTDNS` имеет общий предел 12 секунд. После ошибки или таймаута `MTDNS` переходит к штатному native resolver, поэтому недоступный DoH не удерживает соединение бесконечно. Это означает возможное использование системного DNS при отказе выбранного провайдера.

Отмена, обращение к текущему запросу и callback защищены одним рекурсивным `@synchronized`. Следующая попытка копирует блок под тем же замком и проверяет его перед вызовом: прежний код допускал вызов nil-блока при конкурентной отмене. DNS-парсер ограничивает длину сообщения/имени, проверяет границы указателей сжатия, усечение, opcode и код ошибки. Неправильные ответы завершаются ошибкой и резервным разрешением имени.

## Выполненные проверки

Полный feature overlay применён к закреплённым исходникам Telegram-iOS. Проверены синтаксические деревья изменённых Swift и Objective-C (это не typecheck/компиляция), Python syntax, метаданные и whitespace.

2026-10-04 `scripts/check_doh_providers.py` отправил настоящие DNS A/AAAA из Cloud:

| Провайдер | GET | POST |
| --- | --- | --- |
| Google | успешно | успешно |
| AdGuard | успешно | успешно |
| Mullvad | успешно | HTTP 400 |
| Cloudflare | успешно | HTTP 400 |
| Quad9 | HTTP 503 шлюза Cloud, connection timeout | HTTP 503 шлюза Cloud, connection timeout |

Эти результаты проверяют доступность endpoint из Cloud. Они не доказывают работоспособность iOS-resolver, Quad9 из сети пользователя или отсутствие всех возможных крашей. Пользовательский DoH неизвестен и проверяется приложением при сохранении. Для сообщения о прежнем сбое DNS нет crash/ANR stack trace.

## Обязательная проверка после сборки на iPhone

1. Для каждого таймера 15/30/60 выбрать сервер, который пингуется, но не соединяет аккаунт, при наличии рабочего резерва. Проверить переход по истечении окна, в том числе при `.connecting` без флага проблем и при повторных событиях статуса.
2. Проверить пингующийся, но не достигающий `.online` резерв, недоступные и повторяющиеся серверы, отсутствие рабочего резерва, возврат доступности после следующего прохода.
3. Проверить ручной выбор и выключение использования/автоматики перед дедлайном, удаление кандидата, смену таймера, закрытие настроек, несколько аккаунтов, выход из аккаунта.
4. Проверить кнопку «Проверить все», фоновые проходы при закрытом экране, длинный список и отсутствие накопления запросов/таймеров. Периодические проходы относятся к работающему приложению: iOS может приостановить его в фоне.
5. Для системного DNS и всех DoH проверить холодный запуск, повторный запуск, смену провайдера, плохой URL, HTTP-ошибку, таймаут, отмену во время ответа, резервный native DNS.
6. Проверить потерю/возврат сети, переход Wi-Fi ↔ мобильная сеть, паузу/возврат приложения. При краше сохранить журнал iOS с трассировкой.
