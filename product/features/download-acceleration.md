# Ускорение загрузки

Актуальная интеграция перенесена на Telegram 13.0; [аудит миграции](../../docs/TELEGRAM_13_MIGRATION.md). Ранее указанные результаты №79 и локальных отдельных проверок относятся к прежней базе; новый нативный результат фиксируется отдельно.

Включено в успешную сборку №82 и проверенный IPA 0.4.9. Статус: implemented / compile_passed / device_pending. Опубликованный IPA №79 этой настройки не содержит. Нативная компиляция №82 прошла; скорость на устройстве ещё не измерена.

## Настройка

**Настройки NagramiX → Прочее → Загрузка**:

- «Ускорение загрузки» — выключено при отсутствии сохранённого значения.
- «Ускорение скачивания» — выбор «Штатно», «Среднее», «Максимум», виден только при включённом переключателе, включая глобальный поиск настроек.
- В нижней группе меню — «Выключить»: снимает переключатель, скрывает строку режима и сохраняет выбранный уровень для следующего включения. Отдельной кнопки «Отмена» нет; закрытие меню жестом не меняет настройки.

Ключи iOS: `nagramix.downloads.accelerationEnabled` и `nagramix.downloads.accelerationMode`. Enum raw values: standard = 0, medium = 1, maximum = 2. При отсутствии значения режим — medium, но загрузчик работает штатно, пока переключатель OFF. Неизвестный сохранённый режим возвращает stock limits. Сохранённые ON/OFF и уровень не сбрасываются при старте, обновлении или изменении других настроек.

Штатные ItemListSwitchItem/ItemListDisclosureItem/ActionSheetController используют Telegram presentationData, темы и шрифты. Добавлены RU/EN строки, описание и поиск, stable IDs 117–120 и новая секция в конце enum. Прежние ID/ключи/значения сохранены.

## Фактическая реализация

Изучены MultipartFetch, MultiplexedRequestManager, Network.makeWorker и MultipartUpload точного Telegram-iOS pin. В базе уже есть параллельное скачивание. Для известных больших файлов обычный MultipartFetch имеет 8 частей по 512 КиБ; MultiplexedRequestManager допускает 3 запроса на соединение и 4 соединения на target. Upload использует тот же request manager — глобальное повышение его лимитов изменило бы также отправку файлов.

| Режим | Частей одного подходящего файла | Предел части | Соединений на target для ускоренных частей | Запросов на соединение |
| --- | --- | --- | --- | --- |
| OFF / Штатно | Как в Telegram | Как в Telegram | 4 | 3 |
| Среднее | 12 | 1 МиБ | до 6 | 3 |
| Максимум | 24 | 1 МиБ | до 8 | 3 |

Указанные лимиты — верхние границы, а не гарантированное число открытых соединений или множитель скорости. Фактическая загрузка зависит от размеров и запрошенных диапазонов, сети, прокси, Telegram/DC/CDN и ограничений сервера. Включение может помочь на подходящем соединении; на слабой сети стоит выбрать меньший уровень или выключить.

Настройки и ограниченная таблица tuning размещены в новом NagramiXDownloadSettings.swift существующего Foundation-only модуля NagramiXMediaSettings. TelegramCore получает зависимость только от этого leaf module. Импорт NagramiXCore в TelegramCore не используется: он создал бы зависимость от presentation data с циклом. NagramiXTabSettings сохраняет вложенную модель через свой существующий update.

MultipartFetch делает snapshot перед запуском частей. Tuning применяется только к обычному `.generic` cloud location с известным размером больше 512 КиБ, без secret encryption и вне Stories. Малые файлы, unknown-size, web location и истории сохраняют исходные размеры/параллелизм. Шифрование, file reference revalidation, CDN redirect/AES/hash, retry/FloodWait, приоритеты диапазонов, возобновление и отмена не переделаны. Части остаются внутри штатной границы 1 МиБ и проходят исходные проверки alignment/divisibility.

MultiplexedRequestManager открывает расширенный пул только для resource requests с expectedResponseSize = 1 МиБ. Это размер новой ускоренной части; стандартные части ниже этого порога. Остальные requests, включая upload/control, получают четыре соединения и выбирают только первые четыре существующих context через prefix(4), даже если ускоренная загрузка создала больше соединений. Штатный лимит трёх запросов на соединение, порядок приоритетов, native makeWorker и cleanup сохранены. Новых потоков, собственного transport или download engine нет.

Изменения размера/числа частей применяются к новым fetch instances без перезапуска приложения. Уже начатый файл завершает загрузку с выбранными при старте частями: активные requests не обрываются и не скачиваются заново при переключении. Лимит worker pool читается при следующем native dispatch; после OFF новые requests используют четыре соединения, ранее отправленные завершаются штатно, лишние idle contexts очищает прежний механизм.

## Проверено без нативной сборки

- Raw MultipartFetch, MultiplexedRequestManager, MultipartUpload и Network сверены по Git blob SHA pin `f1dd7a2dbd02cbbf513e75d5695d8d36d1cf5838`; последние два используются только как reference.
- Полный overlay на fresh scoped pin: восемь generated-файлов изменены, новый Foundation-only файл добавлен, 319 файлов совпадают с baseline предыдущих pending-правок. Нижняя панель, double tap/hide reactions, архив, камера, Stories, темы, proxy и остальные прежние generated sources не менялись.
- Семь native exact-вставок в трёх файлах полностью восстанавливают baseline побайтно. 21 missing/duplicate/already-applied случай и повторное применение отклоняются.
- Проверены bounds таблицы (до 1 МиБ/24 частей/8 workers/3 requests), stock paths/upload pool guard и 4000 диапазонов resumed/streaming с native MTProto/CDN alignment/divisibility/boundary constraints.
- Синтаксис шести новых/изменённых Swift-файлов, Python, прежние keys/defaults/IDs, default OFF, conditional mode row и RU/EN uniqueness, metadata/diff пройдены.

Это статические проверки и проверка числовых ограничений. Swift type checking, UserDefaults/UIKit runtime, целостность полученных файлов, стабильность сети, потребление памяти и прирост скорости на iPhone не проверены. Не объявлять ускорение измеренным или гарантированным.

## Приёмка после следующей сборки

1. Чистая установка: OFF, строки выбора режима нет. ON: строка появляется; три режима, отметка выбранного и «Выключить» работают. Закрытие меню жестом не отключает функцию.
2. ON/OFF и выбранный уровень сохраняются после закрытия приложения и изменения другой настройки. «Штатно» с ON даёт native limits. OFF сохраняет уровень, но загрузчик использует stock.
3. На одинаковом Wi-Fi и мобильном соединении сравнить один и тот же большой cloud-файл в OFF/Штатно/Среднее/Максимум после удаления обычного кэша между попытками. Фиксировать время, размер, целостность файла, ошибки и условия сети; не сравнивать скачивание с чтением из кэша.
4. Проверить фото, видео/seek/streaming, документы, голосовые, кружки, обычные/CDN файлы, resume/cancel/revalidation и несколько одновременных загрузок. На слабой сети/через прокси проверить меньшие режимы и OFF.
5. Проверить, что маленькие файлы, Stories, secret/unknown-size/web paths и отправка больших файлов сохраняют штатную работу. Проверить фоновый режим, отсутствие лишних активных запросов после отмены и приемлемую память на физическом устройстве.
6. Во время активного файла переключить уровень и OFF: текущий файл не повреждается, новые fetch instances используют новые настройки, выключение не оставляет неограниченный пул.

Следующий шаг — сборка всего pending batch только по команде пользователя, затем физическая проверка.
